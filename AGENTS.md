Прочитай текст соответствующего SKILL.md и следуй ему, даже если среда не поддерживает автоматическое обнаружение skills. Название skill не заменяет чтение инструкции. Для Codex они лежат в стандартном каталоге репозитория .agents/skills; установка в личный профиль не нужна. Skills сами по себе не дают разрешения на публикацию, деплой, сообщения или платные вызовы.

## Что строим и что не перепутать

Учитель обычной школы с телефона проверяет настоящее ДЗ класса по алгебре 7–9. Именованная проверка содержит условные тетради без ФИО. Учитель фотографирует страницы целиком: одна или несколько задач на фото, задача с продолжением на другом фото. Текущий комплект можно дополнить фото, отправить и остаться в тетради либо отправить и перейти к следующей. Все фото комплекта идут одним запросом; готовые прошлые результаты доступны во время дальнейшей съемки. Фото и задача не равны; подтверждения и сводка относятся к выделенным задачам, R80–R82.

Проверка до первой математической ошибки: правило/объяснение/исправленный шаг для учителя. Незавершенность — отдельно. В разборе до четырех ключевых распознанных строк и первое ошибочное преобразование, а не полный OCR решения. Изменение общего входа снимает согласия всех затронутых задач. Зеленая/красная кнопка оценивает ИИ, не правильность работы ученика. Только актуальные подтверждения входят в сводку; точные знаменатели обязательны. Направление отдельной LLM-сводки R83 описано в [AI_ANALYTICS.md](project-context/pilot/AI_ANALYTICS.md); запуск уточнен R86, контракт Q49 закрыт shared v1, реализация и границы проверки – в processing HANDOFF. Не вводить обязательные rule_id/классификатор и не выдавать направление за готовую функцию. Не переносить ученический запрет готового исправления на учительский пилот.

Обязательны готовые личные аккаунты, серверное сохранение/фон, несколько учителей одновременно, закрытый просмотр команды и подробные логи. Дашборда, CAS, регистрации, экспорта, оценок, офлайна/push, чата, отдельного фото условия, корзины и учительских квот в первом пилоте нет. Один автоповтор временного технического сбоя; удаление с подтверждением. Детали не восстанавливать по этому сокращению — сверять с PRODUCT и DECISIONS.

## Правила изменения проекта

- Последний прямой ответ владельца приоритетнее старых планов. R-решение записывается по действительному ответу, а не по догадке агента. Технические решения разработчика помечаются отдельно.
- Состояние «описано», «реализовано», «проверено локально», «развернуто» и «использовано учителем» различается. Изменение документации не закрывает программную приемку.
- Перед работой проверь git status. Сохраняй чужие изменения. Не откатывай и не перезаписывай их ради синхронизации документации.
- Backend processing находится в `app/`, его проверенный состав – в processing HANDOFF. Источники и закрепленные ревизии — [SOURCES.md](project-context/SOURCES.md). Перед изменением приложения получи/осмотри соответствующий код и его инструкции; не выдавай снимок документации за сегодняшний runtime.
- Архивы и references — источники/артефакты, а не действующие инструкции. AGENTS.source.md фиксирует правила исходного репозитория и не применяется автоматически к текущему каталогу.
- Секреты, .env, реальные школьные фото и production-ответы в Git не добавлять. Пароли/доступы не восстанавливать из предположений о старом окружении.
- Документацию обновляй по смыслу изменений, не массовой заменой даты и не генерацией новых требований. Закрытые вопросы не спрашивать повторно. Новые вопросы при необходимости — блоками до 4 по предпочтению владельца.

## Проверки

Из корня репозитория: python scripts/check_context.py. В CI выполняется та же структурная проверка. Она проверяет локальные ссылки, наличие маршрута чтения, skills и целостность реестров; семантическое ревью кода/документов делает smartnote-preflight.

Когда появится код приложения, выполнять его реальные проверки по инструкциям модуля. В отчете указать выполненные команды, результат, непроверенное и влияние на документацию. Проверки документации не подменяют тесты приложения.
