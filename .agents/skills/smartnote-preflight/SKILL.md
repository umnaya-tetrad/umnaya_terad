# Ревью кода и документации перед публикацией

Используй перед push/merge/подготовкой PR и при завершении существенной задачи. Это ревью текущих изменений, а не разрешение самостоятельно публиковать, мержить или деплоить. Явная команда пользователя о публикации уже является основанием продолжить ее после проверки, без повторного запроса того же разрешения.

Прочитай [AGENTS.md](../../../AGENTS.md); если проект незнаком, сначала smartnote-pilot. Затем:

1. Установи базу сравнения и состав изменения: status, staged/unstaged diff, новые файлы, diff ветки к базе PR. Для первоначального коммита проверь весь набор. Учитывай чужие незакоммиченные правки, не откатывай их.
2. Прочитай реально затронутые части кода и документов. Проверь соответствие согласованным R-решениям и [карте обновления](../../../project-context/AGENT_WORKFLOW.md), а не только формальное наличие Markdown-изменений.
3. Для каждого существенного изменения проверь doc-impact через smartnote-doc-sync. Если документация расходится с кодом/новым подтвержденным решением, обнови ее и повтори затронутые проверки.
4. Выполни python scripts/check_context.py, git diff --check и git diff --cached --check. Для уже закоммиченной ветки/PR проверь также diff к базе; чистая рабочая копия не доказывает проверку коммитов. При первоначальном коммите проверяй весь staged-набор. При наличии приложения выполни проверки его модуля по локальным инструкциям. Не объявляй тест документации или демо тестом рабочего пилота.
5. Проверь состав коммита: нет .env/ключей, реальных школьных фото, production-ответов, кэшей/сборок и случайных вложенных Git-репозиториев. Ссылки должны работать у коллеги после обычного clone, а CURRENT_STATE отражать реальный этап.

Обязательные темы ревью при соответствующем diff: владельцы/роли и приватная выдача фото; жизненный цикл очереди и один автоповтор; неизвестный исход платного запроса и дубли; версии/согласия/удаление; формулы сводки и знаменатели; сырой ответ модели и строгий контракт; логирование без секретов и ложных точных замеров.

Вывод ревью: существенные найденные проблемы, что исправлено, результаты выполненных команд, непроверенное, измененные документы или обоснованное отсутствие doc-impact. Не скрывай невыполненные проверки и не создавай формальное «все готово» без результата.

При существенной нерешенной ошибке не представляй изменение как готовое к слиянию. Исправляй в пределах задачи либо конкретно сообщи препятствие. Если проверки пройдены и публикация уже поручена, выполняй ее и проверь удаленный результат. Отдельного AI-сервиса, платного автозапуска и скрытого Git-hook этот skill не создает.
