# Бенчмарк vision-моделей для «Умной тетради»

Цель — выбрать модель по качеству проверки шагов, задержке, надёжности JSON-контракта и фактической стоимости запроса, а не по одному усреднённому числу.

## Наборы и допустимое использование

Основной внешний набор — [EGE Math Solutions Assessment Benchmark](https://huggingface.co/datasets/Karifannaa/EGE_Math_Solutions_Assessment_Benchmark): 122 русскоязычных решения по семи типам заданий ЕГЭ, с эталонным баллом от 0 до 4. Лицензия набора обозначена как `other`; карточка разрешает исследовательское и образовательное использование. До включения изображений или детальных результатов в продукт, маркетинговые материалы либо публичный репозиторий нужно получить явное разрешение правообладателя.

В бенчмарк подаём только `images_without_answer`: это честный аналог фотографии ученика и не раскрывает модели готовый ответ. `images_with_answer` использовать лишь для отдельной проверки утечки правильного ответа, не для основного рейтинга. `images_with_true_solution` нужны разметчику как справочный материал и никогда не передаются проверяемой модели.

Если у примера несколько страниц (`parts_count > 1`), страницы склеиваются вертикально в памяти с нумерацией; исходные файлы не копируются и не сохраняются в результатах. В сводке такие случаи помечаются отдельно, чтобы не смешивать их с одной фотографией тетради.

Набор годится для итоговой оценки решения, но не даёт автоматического эталона для продукта: его поля содержат балл 0–4, а не номер первой ошибочной строки, тип ошибки или ожидаемый JSON. Поэтому нельзя выдавать «точность первого ошибочного шага» по одному этому датасету.

## Gold-набор для продуктовой точности

Создать версионированный `benchmark_manifest.jsonl` из 40–60 одностраничных примеров, стратифицированный по семи темам и баллам. Включить все редкие примеры с баллом 4, а также примеры с 0–3 баллами. Для каждого примера два преподавателя независимо фиксируют:

- ожидаемый `status`;
- все видимые шаги до первой ошибки;
- номер первой ошибки или отсутствие ошибки;
- класс ошибки из контракта и краткое объяснение;
- замечание о том, достаточны ли для оценки условие и чертёж.

Расхождения разбирает третий преподаватель. Эталон строится по `images_without_answer`; reference solution помогает только при разметке. После фиксации версии этот набор не меняют из-за результатов моделей. Полные 122 примера можно запускать отдельно как стресс-тест и прокси-метрику итогового балла, но не как единственную метрику продукта.

## Первый скрининг: 50 изображений без оценки математической корректности

Первая цель — не объявить модель математически точной, а честно сопоставить, с какой задержкой и ценой она возвращает валидный разбор, а с какой — отказывается распознавать фото.

В текущей версии датасета 28 решений имеют балл 0, 40 — 1, 35 — 2, 11 — 3 и только 8 — 4. Балл 4 — единственный безопасный прокси полностью верного решения; все восемь таких примеров относятся к темам 18 и 19, а четыре состоят из двух страниц. Балл ниже 4 означает «не максимальный балл ЕГЭ», но не доказывает конкретную ошибку преобразования: работа может быть неполной или иметь иной недостаток.

Состав первого запуска:

| Группа | Количество | Источник и правило |
| --- | ---: | --- |
| Неполные или ошибочные | 35 | По 5 одностраничных `images_without_answer` из каждой темы 13–19; только `score < 4`, с перемешанными баллами 0–3 |
| Полностью верные из датасета | 8 | Все `score = 4`; две страницы склеиваются вертикально в памяти и помечаются `presentation=stitched` |
| Полностью верные, внутренние | 7 | Два уже существующих синтетических примера (`01-linear-correct`, `02-fraction-correct`) и ещё пять примеров, проверенных преподавателем, предпочтительно по темам 13–17 |

Таким образом, получается требуемое соотношение 35/15 без ложного объявления частично оценённых работ «правильными». В manifest обязательно записываются `source`, `solution_id` (для Hugging Face), `task_id`, `score`, число страниц и `presentation`. Это позволяет отдельно смотреть, не проигрывает ли модель только на склеенных страницах.

### Что измеряет один запрос

Каждая модель получает одинаковые: изображение, `detail: high`, системный промпт, JSON Schema, `temperature: 0` и лимит генерации. Smoke-скрипт отправляет запросы асинхронно, но с явным лимитом `--concurrency` (по умолчанию 10); задержка конкретного запроса измеряется после получения слота, поэтому время очереди не смешивается с ответом провайдера. В полном сравнении нужно одинаково ограничивать конкурентность всех кандидатов и повторять набор в разные часы.

В одну строку `benchmark-results/<run_id>/requests.jsonl` сохраняются: `case_id`, запрошенная и canonical-модель, версия промпта, время старта, `latency_ms` до полного HTTP-ответа, HTTP-статус, результат контракта, `status`, `overall_confidence`, `usage` (`cost_rub` и токены) и очищенный код ошибки. При успешной валидации сохраняется нормализованный JSON `AnalysisResponse`. Если модель ответила HTTP 200, но не прошла контракт, сохраняется её `raw_response` исключительно в этом локальном gitignored benchmark-файле — чтобы исправлять промпт. Байты изображения, ключ и полный промпт не сохраняются; production-ответы и пользовательские изображения по-прежнему никогда не записываются сырыми.

После запуска строятся два файла:

- `summary.csv` — по модели: число валидных разборов, число каждого `status`, p50/p95 `latency_ms`, медианная/p95 цена, сумма расходов;
- `readability-disagreements.csv` — только случаи, где хотя бы одна модель вернула `ok`, а другая — `needs_clearer_photo` или `insufficient_context`, с ссылкой на `case_id`, статусами, задержкой и ценой всех моделей.

Это напрямую показывает нужный случай «одна модель прочитала фото, другая отказалась», не подменяя его догадкой о математической корректности. Для более устойчивых выводов о задержке после скрининга повторить тот же набор ещё дважды в разные часы и сравнить p50/p95.

Для быстрой регрессии MVP есть `app/run_model_benchmark.py`. Он загружает в память 11 реальных одностраничных изображений `images_without_answer` из Dataset Viewer: пять работ с максимальным баллом 2, пять с баллом 1 и одну работу с баллом 0; только `task_id` 13 и 15. Скрипт дополнительно проверяет `parts_count=1`, score и task_id до отправки модели. В текущем MVP он отправляет 11 запросов к зафиксированной `google/gemini-3.7-flash`. Сам бенчмарк фото не сохраняет.

```bash
docker compose run --rm backend python run_model_benchmark.py
```

Если Docker Desktop не устанавливает прямое TLS-соединение с Polza AI, запустите тот же скрипт на хосте: это не меняет `trust_env=False` у Polza-клиента и использует ключ только из `.env`.

```bash
py -3.12 -m venv .venv-benchmark
.\.venv-benchmark\Scripts\python.exe -m pip install -r app\requirements.txt
.\.venv-benchmark\Scripts\python.exe app\run_model_benchmark.py --output-dir benchmark-results --concurrency 10
```

Чтобы повторить только новых кандидатов, передайте модель несколько раз:

```bash
.\.venv-benchmark\Scripts\python.exe app\run_model_benchmark.py --output-dir benchmark-results --concurrency 10 --model google/gemini-3.7-flash
```

Результаты находятся в `benchmark-results/smoke-*/`; каталог игнорируется Git. Скрипт завершится с ненулевым кодом, если хотя бы один запрос не вернул валидный контракт.

После новых запусков соберите единую локальную историю и обновите безопасную сводку для репозитория:

```bash
.\.venv-benchmark\Scripts\python.exe app\build_benchmark_history.py
```

Команда сохраняет полные записи всех найденных запусков, включая уже сохранённые диагностические raw-ответы, в игнорируемый `benchmark-results/history.json`. В [`benchmark-run-history.md`](benchmark-run-history.md) попадают только параметры, измерения, сводки и решения по моделям — без изображений, ключей и сырого текста.

Когда требуется проверить не только контракт, а математику, сначала применяйте входной фильтр к работам с максимальным баллом, затем вручную фиксируйте оракул для каждого случая с неполным баллом до интерпретации ответа модели. Первый такой результат находится в [`model-math-assessment.md`](model-math-assessment.md).

## Прогон

1. В [`app/model_catalog.py`](https://github.com/svn-re7/SmartNoteLanding/blob/b8423b01a5eb56601539e83d14c382d23eea1a61/app/model_catalog.py) задать `BENCHMARK_MODELS`. Секретный `POLZA_API_KEY` остаётся единственной обязательной переменной в `.env`.
2. До запуска запросить каталог Polza и отфильтровать модели с изображением во входных модальностях и structured output. Зафиксировать ID модели, провайдера и версию промпта.
3. Для каждой пары «модель × пример» отправить один и тот же промпт, JSON Schema и исходное изображение. Выполнять пары асинхронно с зафиксированным лимитом конкурентности и фиксировать его в метаданных запуска.
4. Для первого скрининга выполнить один запрос на пару «модель × пример». Для финалистов повторить тот же набор ещё дважды в разные часы с `temperature: 0`; первый прогон отметить как cold, последующие — как warm. Не включать повторные HTTP-попытки в основное измерение; их считать отдельной метрикой устойчивости.
5. Измерять монотонным таймером начало запроса, момент полного HTTP-ответа и момент завершения Pydantic-валидации. Из API Polza сохранять `usage.cost_rub`, токены и canonical model, но не ключ, изображение или полный промпт. Невалидный сырой ответ разрешено хранить только в локальном gitignored `benchmark-results` для отладки контракта, не в production или UI-срезе.

## Метрики и решение

| Группа | Метрика |
| --- | --- |
| Контракт | доля HTTP-успеха, доля Pydantic-valid JSON, доля отказов по статусам |
| Качество | exact match `status`, exact match номера первой ошибки, macro-F1 класса ошибки, точность распознавания корректного префикса шагов |
| Скорость | p50/p95 времени до полного валидного ответа; cold и warm отдельно |
| Стоимость | медиана и p95 `cost_rub` на изображение, токены, стоимость успешного валидного разбора |
| Надёжность | вариативность результатов между повторами и доля инфраструктурных ошибок |

Сначала отсеять модель с недостаточной надёжностью: менее 99% валидных ответов либо заметно высокий процент необъяснимых отказов. Из оставшихся построить таблицу Парето «качество — p95 задержка — медианная стоимость», а не сводить всё к произвольному единому баллу. Финальное решение подтверждается слепым ручным просмотром всех случаев, где модели расходятся или ошибаются.

## Хранение результатов

В Git хранить только manifest с публичными идентификаторами набора и агрегированную сводку CSV/JSON; сами изображения обычно не скачивать в репозиторий и не сохранять их хеши. Исключение для локального демонстрационного экрана согласовано отдельно: 10 публичных `images_without_answer` smoke-набора лежат в [`inputExamples/benchmark/`](https://github.com/svn-re7/SmartNoteLanding/tree/b8423b01a5eb56601539e83d14c382d23eea1a61/inputExamples/benchmark) с README и manifest происхождения. Для UI экспортируется только нормализованный срез валидированных результатов командой `python app/export_benchmark_snapshot.py benchmark-results/<run_id>`; это не пользовательские фото и не production-данные, а сырой невалидный ответ туда намеренно не попадает. Детальные результаты одного запуска хранить локально в `benchmark-results/<run_id>/` и игнорировать Git: `run.json` с версиями, строка на запрос с метриками, валидированным результатом, причиной ошибки и, только при невалидном контракте, сырым текстом ответа. Правила о несохранении пользовательских фото и сырых production-ответов остаются без исключений.

Когда понадобится сравнение запусков несколькими людьми или в CI, перенести метаданные и валидированные результаты в PostgreSQL отдельными таблицами `benchmark_runs`, `benchmark_cases`, `benchmark_predictions` — без байтов изображений и без API-ключей. Из них строится дашборд и воспроизводимая сводка.

## Polza AI

Polza принимает локальные изображения как Base64 в `image_url` и поддерживает `detail: high`; режим `high` точнее, но медленнее и дороже. Сравнение моделей проводится с одним значением `detail` — для тетрадей это `high`. В ответе Polza возвращает `usage` с токенами и фактическим `cost_rub`, поэтому стоимость нужно брать из ответа, а не из прайса. JSON Schema поддерживается не всеми моделями: для кандидата можно диагностировать `json_schema` и `json_object` через `app/diagnose_polza_model.py`; даже в fallback-режиме ответ проходит ту же Pydantic-валидацию на сервере.

Исходящий клиент в приложении использует `trust_env=False`, то есть игнорирует `HTTP_PROXY` и `HTTPS_PROXY` среды для запросов к Polza AI.
