# Архитектура пилота «Умная тетрадь»

## Принятые решения

Для пилота используем модульный монолит на FastAPI.

- **PostgreSQL** — основная и достаточная БД. Она подходит для связанных сущностей, `JSONB` с меняющимися свойствами LLM и событий аналитики, а также индексов без лишней операционной сложности.
- **Оригинальные фото не сохраняем.** Файл проверяется, передаётся LLM из памяти процесса и удаляется сразу после завершения вызова. В БД остаются лишь метаданные попытки и итог анализа.
- Внешнее **LLM API с поддержкой изображений** подключается через отдельный адаптер. Модель обязана вернуть версионированный структурированный JSON, который валидируется Pydantic до сохранения и показа.
- В первой версии вызов LLM синхронный. Очередь задач (Redis + Celery/ARQ/Dramatiq) понадобится лишь при росте нагрузки или длительной обработке; в очередь нельзя передавать байты изображений без отдельного решения о хранении.
- Ошибки и трассировки: Sentry + OpenTelemetry. Логи приложения — структурированный JSON в stdout и сборщик логов платформы. Не использовать БД аналитики как хранилище технических логов.

PostgreSQL одного достаточно, пока фактическая нагрузка не покажет потребность в ClickHouse, DWH или отдельном хранилище событий.

## Схема системы

```text
Браузер
  │  фото + события продукта
  ▼
FastAPI API ──► PostgreSQL (посетители, попытки, результаты, события)
  │   │
  │   └────────► LLM API (фото только в памяти запроса)
  │                 │ JSON
  └─────────────────┘
          валидированный результат → UI рендерит безопасный Markdown

FastAPI ──► JSON-логи + трассировки + трекинг ошибок
```

## Сценарий обработки

1. Браузер создаёт или использует псевдонимный `visitor_id`. Аккаунты можно добавить позднее.
2. `POST /attempts` принимает изображение и проверяет согласие, MIME-тип, корректность декодирования, размер, разрешение и лимит запросов.
3. API создаёт `attempt`, отправляет изображение в памяти адаптеру LLM и очищает байты после вызова. Копии, ключи объектного хранилища и хеши фото не записываются.
4. Сервер валидирует ответ LLM, сохраняет `analysis_result`, версии модели/промпта, время, метаданные стоимости и ошибку при наличии. Детали провайдера в браузер не отправляются.
5. Клиент получает результат в ответе и показывает только подготовленный сервером Markdown, выделяя `incorrect_step`.
6. Клиент и сервер пишут события с общими `attempt_id` и ID корреляции.

Для публичного MVP дневной лимит реализован отдельными таблицами `daily_quota_usage` и `daily_quota_reservations`. В них есть только HMAC-псевдоним посетителя, дата, счётчик успешно завершённых разборов и короткие технические резервации. Они не содержат IP, фото, OCR-текст, решение или ответ LLM. Резервирование перед вызовом модели не списывает лимит; запись учитывается только после валидного ответа `status=ok`.

Синхронный путь предпочтителен на старте: фото не ждёт в очереди. Переход к асинхронной обработке требует отдельного решения, как передать изображение воркеру, не сохраняя его.

### Важное ограничение загрузки

`UploadFile` FastAPI использует временный spooled-файл и может выгрузить крупный файл на диск. Если обещание «не сохраняем фото» строгое, ограничить размер тела запроса на прокси и читать ограниченное тело в память либо настроить обработку без выгрузки на диск. Не отправлять фото в Redis, очередь, логи, трассировки, отчёты об ошибках или отладочный вывод.

Отсутствие хранения на нашей стороне не означает отсутствия хранения у провайдера LLM. До запуска проверить его настройку и политику ретенции данных.

## Контракт с LLM

Полный согласованный контракт, готовые примеры, JSON Schema и инструкция модели находятся в [`docs/llm-contract.md`](llm-contract.md). Использовать его как единственный источник истины для интеграции. Запрашивать JSON только через structured output и дополнительно валидировать его Pydantic на сервере; не извлекать данные из текста регулярными выражениями. При невалидном ответе, ошибке провайдера или низкой уверенности возвращать понятный статус и возможность повторить запрос, а не выдумывать результат.

## Модель PostgreSQL

| Таблица | Назначение | Важные поля |
|---|---|---|
| `users` | Пользователи с аккаунтом, если появятся | `id`, статус согласий, дата создания |
| `visitors` | Псевдонимная идентичность до входа | `id`, хеш идентификатора браузера, первое/последнее посещение |
| `attempts` | Одна загрузка решения и её жизненный цикл | `id`, `visitor_id`, `user_id?`, статус, время начала/завершения, ID корреляции; без поля фото |
| `analysis_results` | Валидированная интерпретация и обратная связь | `attempt_id`, версии схемы/промпта/модели, нормализованные поля, уверенность |
| `events` | Продуктовая аналитика | `id`, время, ID посетителя/пользователя/попытки, имя события, ID сессии, `properties JSONB` |
| `consents` | Аудит согласий на обработку данных и аналитику | ID субъекта, версия политики, выбор, время |

Индексы: `events (visitor_id, occurred_at)`, `events (session_id, occurred_at)`, `events (name, occurred_at)`, `attempts (visitor_id, created_at)` и `attempts (status, created_at)`. Для часто фильтруемых данных использовать явные колонки, а `JSONB` оставить гибким свойствам событий и метаданным провайдера. Не сохранять байты изображения, ключи хранилища, хеши изображений, OCR-текст или другие производные от фото идентификаторы.

## Метрики

- Воронка: `landing_viewed`, `upload_started`, `upload_completed`, `analysis_requested`, `analysis_completed`, `analysis_failed`, `result_viewed`, `retry_clicked`.
- Вовлечение: длительность сессии, время от входа до загрузки, длительность обработки LLM, время просмотра результата, выход после результата, загрузки на посетителя, возвраты.
- Качество и стоимость: задержка модели, доля невалидных ответов, доля повторов, распределение уверенности, токены/стоимость, оценка «полезно / не полезно».

Каждое событие содержит `occurred_at`, `visitor_id`, `session_id`, опциональный `attempt_id`, страницу/версию, статус согласия и компактный `properties`. Не добавлять IP-адреса, фото, решения, полные промпты и ответы LLM. Если сразу нужны дашборды, можно подключить PostHog, но канонические сущности и жизненный цикл попытки остаются в PostgreSQL.

## Логи, наблюдаемость и приватность

- **Логи:** JSON в stdout: время, уровень, компонент, ID запроса/корреляции, ID попытки, длительность, статус, очищенный код ошибки.
- **Ошибки/трассировки:** Sentry и OpenTelemetry; перед экспортом очищать пользовательское содержимое.
- **Аудит и аналитика:** `events` и `consents` в PostgreSQL, но это не замена техническим логам.
- **Сырые ответы LLM:** не сохранять по умолчанию. При необходимости отладки — шифровать, ограничивать доступ и задавать короткую ретенцию.
- **Фото:** не сохранять, исключать из всех логов и очищать после LLM-вызова.

До публичного запуска нужны уведомление о приватности, правовое основание/согласие, механизм удаления данных и сроки хранения. Тетради могут содержать имена и другие персональные данные.

## Рекомендуемая структура кода

```text
app/
  api/              # маршруты FastAPI и модели запросов/ответов
  core/             # настройки, авторизация, логирование, безопасность
  db/               # модели SQLAlchemy, сессии, миграции Alembic
  services/         # жизненный цикл попытки и оркестрация
  integrations/     # адаптер LLM, поставщики аналитики и ошибок
  workers/          # асинхронные задачи, если появятся
  schemas/          # контракты Pydantic, включая схему ответа LLM
tests/
infra/
docs/
```

## Порядок реализации

1. Определить схему ответа и проверить её на хороших, ошибочных и нечитаемых фото.
2. Реализовать валидацию загрузки, `attempts` без хранения фото и синхронный запрос к LLM.
3. Добавить адаптер LLM, валидацию Pydantic, повторы и безопасный рендеринг UI.
4. Добавить события воронки, структурированные логи, трекинг ошибок, дашборд, согласия и задачи удаления/ретенции.
5. По реальным объёму, задержке, качеству и стоимости решить, нужна ли отдельная инфраструктура.
