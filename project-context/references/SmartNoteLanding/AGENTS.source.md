# SmartNote Landing — инструкция для участников и агентов

## Цель продукта

Сделать лендинг-пилот и первый рабочий сценарий для **«Умной тетради»**: посетитель фотографирует решённую математическую задачу, получает понятное Markdown-объяснение решения и видит конкретный шаг, на котором допустил ошибку.

## Карта проекта

- [Архитектура и модель данных](docs/architecture.md) — согласованная высокоуровневая схема, выбор хранилищ, поток запроса, аналитика, приватность и порядок реализации.
- [Контракт LLM](docs/llm-contract.md) — обязательная JSON-схема результата проверки, примеры, правила валидации и инструкция для модели.
- [Ручная математическая сверка](docs/model-math-assessment.md) — оракул и результаты по первому набору работ с неполным баллом.
- [Демо интерфейса](docs/frontend-demo.md) — запуск React-модуля в Docker Compose и состав мок-сценариев.
- [Сценарий Polza AI](docs/backend-integration.md) — настройка ключа и путь «фото → FastAPI → Polza AI → валидный JSON → UI».
- [.gitignore](https://github.com/svn-re7/SmartNoteLanding/blob/b8423b01a5eb56601539e83d14c382d23eea1a61/.gitignore) — локальные окружения, секреты, загружаемые файлы, логи и файлы IDE, которые нельзя коммитить.
- [.env.example](https://github.com/svn-re7/SmartNoteLanding/blob/b8423b01a5eb56601539e83d14c382d23eea1a61/.env.example) — безопасный шаблон переменных Polza AI; настоящий `.env` не коммитится.
- [compose.yaml](https://github.com/svn-re7/SmartNoteLanding/blob/b8423b01a5eb56601539e83d14c382d23eea1a61/compose.yaml) — контейнеры разработки фронтенда (`5173`) и FastAPI (`8000`).
- `src/` — React-компоненты, типы контракта, моки, интерфейс отправки фото и стили модуля разбора решения. `src/components/LandingPage.tsx` — единственная публичная главная с проверкой фото; `src/components/InternalTools.tsx` — лениво загружаемые демо, импорт JSON и бенчмарк, доступные только с `VITE_ENABLE_INTERNAL_TOOLS=true` по `/internal`.
- [`examples/analysis-response-example.json`](examples/analysis-response-example.json) — валидный пример ответа LLM для ручного теста вкладки импорта.
- `inputExamples/` — пять синтетических PNG с алгебраическими решениями и SVG-исходники; используются реальным e2e-скриптом `app/run_e2e_examples.py`. В `inputExamples/benchmark/` — только 10 публичных одностраничных фото `images_without_answer` заданий 13 и 15 из внешнего датасета и манифест происхождения, для локального экрана сравнения (не пользовательские загрузки).
- `app/` — FastAPI-приложение: валидация изображения, клиент Polza AI, промпт, контракт, локальные benchmark-скрипты и тесты в `app/tests/`.
- `app/model_catalog.py` — выбранная модель приложения и воспроизводимый список кандидатов для офлайн-бенчмарка; ключи сюда не добавлять.
- `app/quota.py` и `app/migrations/001_daily_quota.sql` — анонимный дневной лимит: HMAC-псевдоним cookie, PostgreSQL-резервации и списание только после успешного валидного разбора.
- `app/run_model_benchmark.py` — smoke-бенчмарк Polza AI: 10 реальных одностраничных фото заданий 13 и 15 из Dataset Viewer на каждую модель, задержка, usage, версия промпта и валидированный контракт.
- `app/export_benchmark_snapshot.py` — экспорт безопасного среза валидированных benchmark-результатов для UI.
- `app/build_benchmark_history.py` — сбор всех локальных запусков в `benchmark-results/history.json` и безопасной истории решений в `docs/benchmark-run-history.md`.
- [Бенчмарк моделей](docs/model-benchmark.md) — методика сравнения качества, задержки и стоимости vision-моделей.
- [История прогонов](docs/benchmark-run-history.md) — сводки найденных запусков и решения по моделям без сырых ответов.
- `tests/` — автоматические тесты верхнего уровня; создавать вместе с будущим кодом приложения.
- `infra/` — конфигурация деплоя, миграций и наблюдаемости; создать при добавлении инфраструктуры.

Обновлять этот список при добавлении, переименовании или удалении важных файлов и папок проекта.

## Обязательные правила реализации

- Использовать FastAPI для бэкенда и PostgreSQL как основную базу данных. Перед добавлением нового сервиса сверяться с архитектурным документом.
- Не коммитить секреты, загруженные пользователями изображения, сырые ответы LLM из продакшена и локальные логи. В пилоте не сохранять оригиналы фото: обрабатывать изображение в памяти и удалять его байты после завершения LLM-запроса. Для конфигурации использовать переменные окружения и публиковать только безопасный `.env.example`.
- Валидировать загруженные файлы (MIME-тип, декодирование изображения, размер и разрешение) до передачи LLM.
- Считать любой ответ LLM недоверенным: требовать версионированную JSON-схему, валидировать её на сервере и при неудаче показывать понятное состояние ошибки с возможностью повторить запрос.
- Не заявлять о математической достоверности, если модель не уверена. Передавать пользователю уверенность модели и её ограничения.
- В аналитике использовать псевдонимный идентификатор посетителя, минимизировать персональные данные и запрашивать согласие до запуска необязательного трекинга.

## Рабочие соглашения

- Оставлять API-маршруты тонкими: бизнес-логику, адаптеры LLM, работу с БД и аналитику разносить по отдельным модулям.
- Добавлять миграцию БД к каждому изменению схемы и тесты для разбора JSON-схемы и критичных маршрутов.
- Вести логи в JSON и добавлять ID запроса/корреляции. Не записывать содержимое изображений, API-ключи, полные промпты или ответы с пользовательскими данными.
- Передавать в UI только данные, прошедшие серверную валидацию контракта LLM. В демо используются локальные моки из `src/data/`.
