## 2. Выбранное техническое направление

| ID | Решение разработчика | Причина / граница |
|---|---|---|

| T03 | Долговечная очередь в PostgreSQL с коротким атомарным захватом задания, lease и отдельными попытками | Не вводим Redis/Celery как обязательный новый сервис для небольшого пилота; ресурсы сервера и пропускная способность еще проверяются |

| T05 | Личные учетные записи, серверные сессии в защищенной cookie; создание и сброс доступа командой | Нет регистрации, SMS/email-процесса или отдельного администратора аккаунтов в первом объеме. Конкретные реквизиты выдаются вне Git |
| T06 | Получение статусов коротким polling только видимой страницы с восстановлением после возврата | Достаточно для готовых задач без push/WebSocket-сервиса. Интервал настроить по измерениям, не делать его заметной частью 5–15 секунд |
| T07 | Неизменяемые версии входа/разбора, отдельный изменяемый отзыв с контролем версии | Нет наследования старого согласия и тихого перетирания с другого устройства |
| T08 | Пометка удаления с аудитом и исключением из активных выборок; подтверждение в UI | Нет корзины/восстановления. Это не обещание физического стирания фото/истории |
| T09 | Закрытый раздел поддержки в том же приложении, серверная роль staff_read; аналитика — логи | Обязательный просмотр материалов без отдельного аналитического дашборда и без правки отзывов за учителя |
| T10 | Один проверяющий запрос по совместному комплекту фото с массивом независимых задач и связями продолжений | Основание R80 и локальный эксперимент. Точный промпт/контракт — AI_INTEGRATION; это кандидат интеграции, не готовый production-пилот |

Выбор PostgreSQL для очереди — наше проектное решение. Документация PostgreSQL 16 описывает SKIP LOCKED как подходящий механизм для нескольких потребителей очереди; это не механизм расчета согласованной сводки. [Первичный источник PostgreSQL](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE).

FastAPI BackgroundTasks выполняет работу после ответа; для пилота отдельно требуется долговечность состояния и восстановление работы. Поэтому одного вызова BackgroundTasks без сохраненного задания недостаточно для выбранной архитектуры. Это вывод из требований, а не обещание фреймворка. [Документация FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/).

| Review | Конкретный Analysis, agree/system_error, необязательный комментарий, версия отзыва/время/автор; математический вывод не перезаписывается |
| Event / Audit / Usage | Раздельные журналы продукта, действий команды и вызовов/расходов; ссылки на материалы вместо копий содержимого |

Все дочерние сущности проверяются через владельца родительской проверки. Нельзя открыть чужое фото или изменить отзыв, просто зная ID. Доступ staff_read проверяется на сервере и журналируется; frontend-флаг не является разрешением.

Точное физическое именование таблиц, индексы и миграции — часть разработки. Уникальность активного запуска и ключей идемпотентности должна обеспечиваться сервером/БД, а не только блокировкой кнопки.

## 4. Состояния обработки и результата

| Слой | Состояния проекта | Значение |
|---|---|---|
| Вход | draft → sealed | Набор страниц еще редактируется или зафиксирован для отправки |
| Job | queued → running → ready / uncheckable / failed | Очередь, исполнение, валидный разбор, недостаточный вход/отказ, техническая неудача |
| Дополнительное ожидание | retry_wait / waiting_funds | Разрешенный автоповтор или ожидание ресурса; не ошибка ученика |
| Удаление/замена | cancelled / superseded | Запуск исключен из актуального состава; поздний ответ не возвращает его |
| Математика | no_error / first_error | Корректность имеющихся шагов, независимо от завершенности |
| Завершенность | complete / incomplete / undetermined | Не смешивать с отсутствием найденной ошибки или сетевым сбоем |
| Отзыв | pending / agreed / system_error | Просмотр без кнопки остается pending |

Переходы обработки не создают согласия. Красная отметка не запускает повтор, не меняет no_error на first_error и не отключает сервис. Неудача по фото/условию не становится математической ошибкой. Счетчики считаются по текущим сущностям, а не по журналу попыток.

## 5. Отправка и долговечная очередь

1. Клиент добавляет фотографии страниц в draft комплекта одной тетради; граница submit определяется действием отправки R81. После завершения группы сервер проверяет тип/декодирование/ориентацию, принадлежность, сохранение страниц и согласованный порядок.
2. Вход фиксируется; транзакция создает один Job с ключом идемпотентности. Ответ принятия содержит ID задания и подтвержденное состояние. Потерянный ответ не должен заставлять клиента создать второй платный запуск.
3. Worker короткой транзакцией захватывает доступное задание и записывает lease/идентификатор попытки. Блокировка строки не удерживается на протяжении обращения к модели.
4. Проверяются активность комплекта/родителей и финансовый резерв. Один вызов Polza получает все упорядоченные фото конкретной версии комплекта; ответ может содержать несколько задач.
5. Ответ проходит серверную валидацию, согласование выделенных задач и привязок фото. Временный task_id модели не является ID БД. Сохранение общего Analysis/результатов задач и завершение Job атомарны с проверкой поколения/lease; старый исполнитель не публикует новый актуальный результат.
6. Клиент получает текущее состояние, показывает доступные результаты прошлых комплектов по готовности во время дальнейшей съемки, без принудительного прерывания камеры. Статусы серверные, закрытие вкладки не отменяет Job.

После рестарта worker восстанавливает сохраненное состояние. Истекший lease требует проверки, а не слепой повторной отправки: если предыдущий вызов мог быть принят провайдером, его результат/стоимость могут быть неизвестны. Отмечать неопределенную попытку для разбора, не обещать exactly-once внешнего API без поддержки провайдера. Эта защита не должна создавать бесконечные автоповторы.

Конкурентность настраивается глобально; несколько учителей могут работать одновременно. Очередь не должна смешивать владельцев или надолго вытеснять остальных одним комплектом. Точная емкость на существующем сервере выясняется измерениями.

## 6. Один автоматический повтор

R78: максимум один автоматический повтор временного технического сбоя в одном запуске — исходная попытка плюс не более одной повторной. Ручной повтор создает новый связанный запуск; старые попытки не превращаются в новые задачи.

Кандидаты на повтор — подтвержденный временный отказ провайдера/сети, если повтор не является слепым дублем уже исполняющегося запроса. Причины вроде 429/5xx и допустимое ожидание сверяются с реальным адаптером/провайдером. Ошибка учетных данных, неприемлемый файл, недостаточное условие, неверный математический вывод, красная отметка и постоянная ошибка контракта не должны циклически повторяться.

Перед повтором снова проверить активность, остаток средств и попытки. После исчерпания разрешенного повтора показать техническую неудачу с ручным повтором, пересъемкой или пропуском. Остальные задачи продолжаются. Повторы после перезапуска не обнуляют счетчик попыток. Технический timeout не равен целевым 15 секундам.

## 7. Контракт анализа и математических правил

Проверенный экспериментальный контракт page-check/1.2 и точный промпт — в [AI_INTEGRATION.md](AI_INTEGRATION.md), [ai/README.md](ai/README.md). Он возвращает до четырех ключевых строк evidence, а не полную транскрипцию; этот объем принят владельцем по R82 (Q48 закрыт). Свободное rule сохраняется как есть; формальный rule_id не обязателен для текущего checker. Направление группировки отдельным LLM-запросом описано в AI_ANALYTICS. Существующая схема лендинга 1.0 запрещает лишние поля и валидирует префикс до первой ошибки. Для вызова модели используем замороженный page-check/1.2. Собственная доменная API-обертка приложения версионируется отдельно и добавляет сохраненные ID/версии/отзывы; это не повод менять промпт или AI-схему без нового сравнения. Pydantic, TypeScript, рендер, fixtures и агрегаты согласуются с обоими слоями. Старые benchmark-результаты не объявляются данными новой версии.

| Часть нового результата | Содержание |
|---|---|
| Идентификация | Версия схемы и серверная связь с Task/InputVersion/Attempt; модель не назначает владельца или ID БД |
| Outcome | result: all_steps_correct / first_error_found / not_assessed; причина невозможности проверки отдельно от математической ошибки |
| Problem / Evidence | Распознанное условие и до четырех выбранных ключевых строк, R82; не обещать полный список шагов или полный OCR |
| FirstError | В проверенном ответе wrong_latex, rule, explanation, corrected_latex и photo_index; приложение привязывает ошибочный шаг к результату/фото и сохраняет свободный текст правила, не меняя замороженный контракт |
| Completion / Detail | completeness: complete / incomplete / unknown; detail_level различает omitted_steps и partial, с отдельными пояснениями. Недетализированная правильная запись сама по себе не математическая ошибка |
| Гипотеза описки | Допустима как осторожное текстовое пояснение, не отдельный счетчик/диагноз ученика; не добавлять новое обязательное поле к замороженной AI-схеме |


Готовый разбор и отказ проверяются на непротиворечивость: first_error соответствует первому ошибочному переходу среди ключевых строк и оригинальных фото; сокращенный evidence не доказывает транскрипцию каждого предыдущего шага, all_steps_correct не содержит first_error. Незавершенность и корректность независимы. Не искать пропущенные номера ДЗ и не выводить полное решение вместо коррекции первого шага.

## 8. Версии, изменения и сводка

Изменение общего фото фиксирует новый InputVersion комплекта и снимает согласия всех затронутых разборов. Состав/границы задач могут измениться; перенос по task_id/порядку/похожей формуле запрещен. Повтор старой версии не наследует его автоматически. Поздний старый результат не заменяет текущий. Разбор неизменяем; отзыв изменяется с expected_version, чтобы два устройства не затирали друг друга молча.

Добавление отдельного нового комплекта/задач не сбрасывает подтверждения прежних незатронутых комплектов, но меняет полноту тетради. Добавление страницы к уже разобранному комплекту создает новую версию и снимает согласия всех его затронутых задач. Удаление задачи/тетради/проверки с подтверждением исключает потомков из активного состава; очередь не начинает новые платные вызовы по удаленному, поздний ответ не восстанавливает его. Нет корзины/кнопки восстановления. Физическая очистка исходников отдельно не определена.

Сводку вычислять по согласованному текущему snapshot/revision, первоначально на сервере без отдельного материализованного дашборда. После изменения согласия/состава вернуть свежую ревизию. Среднее использует только непустые полностью подтвержденные тетради, топ — актуальные подтвержденные ошибки, в том числе из частичных; знаменатели показываются. Полные определения — [SUMMARY_METRICS.md](SUMMARY_METRICS.md).

| Контур | Операция / ответ |
|---|---|
| POST /api/session, DELETE /api/session, GET /api/me | Вход, выход, собственная роль; серверная защищенная сессия |
| GET/POST /api/checks, GET /api/checks/{id} | Список, создание с названием, актуальный состав/ревизия |
| POST /api/checks/{id}/notebooks | Новая условная тетрадь без ФИО |
| POST /api/notebooks/{id}/tasks | Новая задача, в том числе после возврата |
| POST /api/tasks/{id}/inputs и загрузка страниц | Draft новой версии, порядок фото, подтвержденное сохранение |
| POST /api/tasks/{id}/submit | Seal входа и идемпотентное принятие Job; 202 с ID/состоянием |
| GET /api/tasks/{id}, GET /api/checks/{id}/summary | Текущие статусы/разбор/отзыв и согласованная сводка |
| GET /api/assets/{id} | Закрытая выдача фото после проверки полномочий |
| PUT /api/analyses/{id}/review | Отметка/комментарий с expected_version; конфликт не перетирается |
| POST /api/tasks/{id}/retry | Один ручной новый запуск по актуальному входу, защита от дубля |
| DELETE /api/tasks/{id}, /api/notebooks/{id}, /api/checks/{id} | Подтвержденное в UI удаление с проверкой владельца и ревизии |
| GET /api/staff/checks и детали/материалы | Закрытый просмотр команды, аудит; без endpoint правки отзывов учителя |
| POST /api/events | Пакет нормализованных событий с дедупликацией и ограниченными параметрами |

Граница входа с cookie, защита запросов изменения и политика origin настраиваются сервером. Ни роли, ни принадлежность, ни параметры финансового контроля нельзя принимать из клиентского доверенного флага. Ошибки API различают отсутствие прав, конфликт версий, некорректный файл, неподтвержденный прием и ограничение сервиса.

## 10. Размещение, средства и эксплуатация

Пилот заменяет публичный лендинг на существующих сервере и домене. При разработке сверить ОС/ресурсы, текущие сервисы, HTTPS/reverse proxy, БД/volume и резервирование. Не публиковать dev-порты/режим reload как готовую эксплуатационную конфигурацию. Перед заменой подготовить резервную копию и откат; старый репозиторий не удалять.

Ориентир 400 ₽ в месяц не является жестким месячным стопом или доказанным расчетом достаточности. Учителю не показываются квоты, цены, тарифные счетчики или пополнение. Ограничения 3/день и максимум 20 из лендинга исключаются из пилотного пути, включая серверные проверки и сообщения.

Перед платным вызовом нужен атомарный контроль доступных средств с учетом параллельных резервов/уже запущенных попыток. Возможности баланса/цены/usage Polza и верхнюю оценку стоимости сверить при интеграции; при невозможности надежно проверить средства не обещать гарантированное отсутствие перерасхода и не запускать бесконтрольные вызовы. Команда мониторит и пополняет баланс. Рабочее поведение при нехватке — ожидание пополнения новых платных запусков с сохранением принятых задач и доступа к материалам; это состояние сервиса, не «у учителя закончился лимит».

Логи продукта, технических сбоев, расходов и доступа команды отделяются; содержимое работ/секреты в них не копируется. Дашборда нет. Подробности — [ANALYTICS.md](ANALYTICS.md), [DATA_AND_ACCESS.md](DATA_AND_ACCESS.md).

Приостановку по качеству решает команда вручную. Число красных отметок не выключает сервис автоматически; техническая/финансовая защита независима. Восстановление из резервной копии и согласованность БД/файлов — эксплуатационные проверки, не пользовательская корзина.

## 11. Что нужно проверить при реализации

После R80 граница комплекта/момент отправки определены R81, Q47 закрыт. Q48 закрыт R82: используем проверенный компактный evidence и описание первой ошибки/правила. Остаются фактические проверки окружения: сервер/доступ/емкость, реальная модель и совместимость нескольких фото, цены/остаток и корректность резерва, форматы фото Android/iPhone, миграции, восстановление очереди и скорость. Они имеют измеримый результат и не заменяются утверждением о готовой документации.

## Дополнение R80: интеграция общего входа

Task/Review/сводка остаются на уровне независимой задачи, Job/InputVersion могут охватывать несколько задач. Пустая, неразобранная или неудачная выдача комплекта не делает тетрадь полностью проверенной. Старые согласия измененного комплекта исключаются до нового подтверждения. Удаление задачи не удаляет молча общую фотографию соседних задач; tombstone и поздний ответ не восстанавливают удаленное. Согласование новых выделений — часть реализации, не готовая миграция.

Предложенные 25 000 токенов и новый таймаут являются технической рекомендацией, а не проверенной конфигурацией. Прогоны использовали 12 000/24 000. Политика до трех экспериментальных попыток и локальный бюджетный журнал не переносятся в продукт: R78 сохраняет один автоповтор временного сбоя.

## Семантика действий комплекта по R81

«Добавить фото к комплекту» изменяет только draft. Оба действия отправки фиксируют одну версию всех его фотографий и один Job; повторный клик/потеря ответа не создает второй платный запуск. После «Отправить на проверку» текущая тетрадь сохраняется и открывается новый draft. Вариант с переходом отмечает завершение текущего ввода и открывает следующую тетрадь, не ожидая ready от модели. Это не permanent seal Notebook/Check: можно вернуться и добавить материалы позже. Прием считается состоявшимся только после надежного сохранения. Комплекты разных тетрадей не смешиваются. Готовые разборы прежних комплектов доступны во время следующей съемки.

## Направление AI-сводки R83: проработка отложена

Владелец предложил после полной итерации класса собрать сохраненные JSON разборов по условным тетрадям и отдельным запросом с другим промптом получить JSON сводки/топа. Это направление следующего проектирования, не проверенный пайплайн и не готовая схема/промпт. Формальные rule_id в текущем checker не обязательны: сохраняем исходный first_error.rule, математический вывод, версии и связи с задачами для последующей группировки.

Согласованные формулы, подтверждения и знаменатели сохраняются. Спорное показывается отдельно; не превращается в подтвержденные математические ошибки. Устаревший AI-агрегат после изменения состава/отзыва нельзя показывать как актуальный. Требование обновляемой сводки R46/R63 не отменено: триггер отдельного запроса, частота/момент обновления, snapshot, формат ответа, валидация и поведение при изменении/сбое отложены в Q49; P06 зависит от этой проработки. Обязательного детерминированного классификатора по каталогу и нового поля в замороженном checker нет. [AI_ANALYTICS.md](AI_ANALYTICS.md) фиксирует границы направления.
