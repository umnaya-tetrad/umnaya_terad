## APP-F01. Вернуть изменение фото пропущенного комплекта до финала

**Приоритет: P2. Статус: open.** Связь: APP-10, APP-C21/C28; [UX S05](../shared/ux-flows.md) и [мобильный UX](../shared/MOBILE_UX.md).

**Цель:** учитель может вернуться к пропущенному комплекту и явно изменить его фото, пока состав проверки не зафиксирован.

**Найдено и проверено:**

- [NotebookScreen.tsx](../../../../src/pilot/screens/NotebookScreen.tsx), строки 219–221: само действие изменения фото требует `skippable(bundle)` либо draft; наличие `can_retry` открывает только внешний блок действий и не возвращает изменение фото.
- [flow.ts](../../../../src/pilot/state/flow.ts), строки 11 и 32: задачи пропущенного комплекта исключены из списка, а `skippable` для него false. Альтернативного входа через карточку нет.
- [repository.py](../../../../app/pilot/domain/repository.py), строки 110–112, возвращает `can_retry=false` для skipped. [mutations.py](../../../../app/pilot/domain/mutations.py), `create_input_version` со строки 286, допускает новую версию такого комплекта до финала.
- В реальном локальном HTTP-стеке после `blocked → skipBundle` получены `skipped=true`, `draft=null`, `can_retry=false`; создание версии по текущим фото вернуло 201. Браузер при таком состоянии не предлагает изменение фото.

**Воспроизведение без платных вызовов:**

1. В браузерном тестовом адаптере по образцу [browser_smoke.mjs](../../../../scripts/pilot/browser_smoke.mjs) вернуть для `getCheck` состояние `skipped-unknown-attempt-reserve-retained` из [lifecycle.json](../shared/api/fixtures/lifecycle.json). Приватный asset заменить синтетическим [synthetic-photo.png](../shared/api/fixtures/synthetic-photo.png), как в существующем smoke. Вернуть ETag текущей revision.
2. Открыть эту проверку и «Тетрадь 1». Фаза `review`, у комплекта есть sealed input, `skipped=true`, draft отсутствует, `can_retry=false`.
3. Убедиться: видна отметка пропуска, но нет действия «Изменить фото» и нет карточки, через которую его можно открыть.
4. Для интеграционного подтверждения повторить на изолированном fixture-стеке: получить blocked комплект, вызвать `POST /api/bundles/{bundle_id}/skip`, перечитать Check, затем вызвать `POST /api/bundles/{bundle_id}/versions` с `photo_ids` из текущего sealed input. Использовать текущую revision и отдельный UUID-ключ для каждого нового намерения. Сервер разрешает создание версии — 201.

**Ожидается:** до `finalized` доступен явный переход к изменению фото того же комплекта с существующим предупреждением о последствиях для общего входа. До нового submit сохраняется пропуск и прежний результат; после явной отправки действует новый вход по общему контракту. После финала изменение состава скрыто и запрещено сервером.

**Пути доработки:** `src/pilot/screens/NotebookScreen.tsx`, при необходимости `src/pilot/state/flow.ts`, соседние UI-тесты. Общий API и processing-порты использовать без обхода.

**Ограничения и регрессии:** не включать `can_retry` принудительно, не считать skip подтверждением ИИ или удалением, не освобождать неизвестный финансовый hold. Не добавлять слепой повтор неизвестного запроса. Сохранять подтверждение замены общего входа, revision/idempotency, соседние независимые комплекты и запрет изменения состава после финала.

Связанное расхождение доказательств: в `lifecycle.json` состояние `skipped-failed-bundle-stays-partial` (со строки 1135) содержит `can_retry=true` (строка 1166), а текущий runtime для skipped возвращает false. Учесть оба входа в тестах и согласовать fixture с владельцем processing/shared. Это не отдельная пятая задача и не основание разрешить retry вопреки серверной capability.

**Готово, когда:** браузерный тест открывает замену фото skipped-комплекта с `can_retry=false`; интеграционный тест создает draft, отменяет его без изменения текущего результата, затем проверяет явную новую отправку. В finalized кнопки нет; сценарии unknown/skip сохраняют финансовый учет и не создают автоматического запроса.

## APP-F02. Показывать источник каждой распознанной строки

**Приоритет: P2. Статус: open.** Связь: APP-09, APP-C13/C15; [UX S06, result.lines](../shared/ux-flows.md) требует строки с номерами фото.

**Цель:** учитель различает, с какого снимка взята строка и где находится первый ошибочный шаг, когда решение продолжается на следующей странице.

**Найдено и проверено:** [TaskCard.tsx](../../../../src/pilot/components/TaskCard.tsx), строка 24, выводит только `line.latex`, игнорируя `evidence.photo_index`; строка 29 также не показывает `first_error.photo_index`. В браузере для продолжения M06 есть миниатюры обоих снимков, но у строк и ошибочного шага нет источника.

**Воспроизведение:**

1. Подать `two-photo-continuation` из [lifecycle.json](../shared/api/fixtures/lifecycle.json) через тестовый HTTP-адаптер с синтетическими assets.
2. Открыть готовые разборы и перейти ко второй задаче. Ее исходный пример — вторая Task из [M06.response.json](../../ai/examples/M06.response.json): `photo_indices=[1,2]`, первый ошибочный шаг относится к фото 2.
3. Сопоставить отображение с `evidence[*].photo_index` и `first_error.photo_index` в JSON. Сейчас карточка сохраняет формулы, но не показывает эти номера рядом с соответствующими строками.

**Ожидается:** компактные понятные подписи номера фото рядом с evidence и первым ошибочным шагом. Подписи используют действительную нумерацию текущего комплекта, согласованы с миниатюрами и единым каталогом текста. Продолжение остается одной задачей; одна или несколько задач общего фото сохраняют независимые отзывы.

**Пути доработки:** `src/pilot/components/TaskCard.tsx`, его тесты; при необходимости `src/pilot/screens/ReviewScreen.tsx` и стили. Использовать существующие поля и copy convention. Если не хватает строки каталога, согласовать малое дополнение shared с владельцем, не создавать второй словарь.

**Ограничения и регрессии:** не менять математические формулы, JSON/модель/схему, порядок фото и значения индексов; не выдумывать полный OCR. До четырех evidence-строк, безопасный KaTeX и текстовый fallback сохраняются. Проверить K01, E_C01, M06, single-task/two-photo и много задач на одном фото.

**Готово, когда:** тест сверяет подпись каждой отображаемой evidence-строки с ее `photo_index`, а первого ошибочного шага — с его индексом; браузерный сценарий M06 явно показывает фото 2 у ошибки. Формулы и отдельные отзывы не изменились, 320 CSS px и увеличение текста до 200% остаются читаемыми.

## APP-F03. Сохранить накопленные события перед выходом из аккаунта

**Приоритет: P2. Статус: open.** Связь: APP-13, APP-C29/C35; [требования к событиям](TASKS.md) и [HTTP-контракт](../shared/API_CONTRACT.md).

**Цель:** штатный logout не уничтожает еще не отправленные наблюдения текущей короткой сессии.

**Найдено и проверено:** [useLifecycle.ts](../../../../src/pilot/telemetry/useLifecycle.ts), строки 20–29: обычная отправка раз в 30 секунд; cleanup удаляет таймер и слушатели без отправки очереди. В реальном локальном браузере путь вход → сводка → материалы → разбор → logout занял 1,079 секунды, запросов `/api/events` было **0**. Очередь теряется при размонтировании TeacherApp. Закрытие страницы отдельно обрабатывается через `pagehide`; дефект относится к logout без закрытия вкладки.

**Воспроизведение:**

1. В изолированном fixture-стеке подготовить сохраненную проверку со сводкой и готовой задачей; например, пройти существующий [browser_compose_smoke.mjs](../../../../scripts/pilot/browser_compose_smoke.mjs).
2. В новом браузерном контексте начать перехват запросов `POST /api/events`. Войти синтетическим аккаунтом и открыть сохраненную проверку.
3. Открыть материалы, затем разбор и нажать «Выйти» раньше первого 30-секундного интервала. Не скрывать и не перезагружать вкладку.
4. Дождаться экрана входа. Сейчас запросов событий нет, хотя `app_visible` и `result_opened` были поставлены в очередь.

**Ожидается:** накопленные события и корректное завершение текущего просмотра передаются, пока действительна сессия их автора, **до revoke/logout**. Ошибка или зависание сети не блокирует выход и дальнейший вход; завершение сессии остается надежным. Простая отправка из cleanup после отзыва cookie проблему не решает.

**Пути доработки:** `src/pilot/telemetry/useLifecycle.ts`, `src/pilot/telemetry/client.ts`, `src/pilot/auth.ts`, при необходимости связка в `src/pilot/PilotApp.tsx`, соответствующие unit/browser-тесты. Сохранить общий ingest endpoint и серверное определение автора.

**Ограничения и регрессии:** повтор доставки использует прежние event IDs, без дублирования принятых событий; batch не больше 100. Не переносить очередь и контекст прежнего аккаунта новому пользователю, включая другой tab, 401 и неуспешный logout. События не содержат пароль, cookie, комментарий, фото, математику или сырой ответ. Сбой телеметрии не блокирует фото, отзыв, финал или logout. Не обещать гарантированную офлайн-доставку либо точное рабочее время.

**Готово, когда:** браузерный тест короткой сессии с доступной сетью подтверждает прием ее событий под исходным пользователем до logout; тесты сетевого отказа/зависания разрешают выйти. Проверены одновременный периодический flush, повтор доставки с теми же IDs, отсутствие дублей и смена аккаунта без переноса событий. `visibilitychange`/`pagehide` продолжают работать.

## APP-F04. Убрать горизонтальную прокрутку сводки при крупном тексте

**Приоритет: P3. Статус: open.** Связь: APP-12/15, APP-C30; [мобильный UX](../shared/MOBILE_UX.md), одна колонка от 320 CSS px и доступность при увеличении текста до 200%.

**Цель:** длинные подписи показателей сводки остаются внутри карточки, не расширяя всю страницу.

**Найдено и проверено:** [SummaryScreen.tsx](../../../../src/pilot/screens/SummaryScreen.tsx), строки 38–48, и [pilot.css](../../../../src/pilot/styles/pilot.css), правило `.metrics` около строки 132. В headless Chrome при viewport 320 CSS px и `html { font-size: 36px !important; }` вместо базовых 18 px готовая сводка расширяет страницу до **326 px**. У длинных слов в элементах `li` метрик нет достаточного переноса. На обычном размере текста этот сценарий укладывается в 320 px.

**Воспроизведение:**

1. Открыть готовую сводку `saved-analytics` из [lifecycle.json](../shared/api/fixtures/lifecycle.json) через браузерный тестовый адаптер. Тот же эффект проверен на готовой сводке реального локального fixture-стека.
2. Использовать Chrome-контекст `viewport: { width: 320, height: 760 }`, `isMobile: true`, `hasTouch: true`.
3. Увеличить базовый текст до 200%: `html { font-size: 36px !important; }`. Это способ эмуляции крупного текста, не проверка физического телефона.
4. Проверить подписи «Без найденных математических ошибок» и «В расчете полностью подтвержденных тетрадей», затем сравнить `document.documentElement.scrollWidth` с шириной заданного viewport. Получено 326 вместо 320; в мобильном контексте `innerWidth` также может увеличиться до 326, поэтому сравнивать только с ним недостаточно.

**Ожидается:** подписи и числа видны целиком, ширина страницы не превышает заданные 320 CSS px. Для длинных формул допустима локальная прокрутка внутри формулы; она не должна превращаться в прокрутку страницы.

**Пути доработки:** `src/pilot/styles/pilot.css`, при необходимости структура метрик в `src/pilot/screens/SummaryScreen.tsx`, браузерная проверка соседних экранов.

**Ограничения и регрессии:** не уменьшать шрифт или кнопки ради размещения, сохранить цели нажатия от 48 px, межстрочный интервал и текст показателей. Не скрывать переполнение страницы так, чтобы обрезать смысловой текст. Сохранить локальную прокрутку математики, работу фото-zoom и нормальный desktop layout.

**Готово, когда:** браузерный assert проверяет `scrollWidth` относительно заданного viewport для сводки на 320/375/390/1280 CSS px при 100%/200% текста; длинные подписи не обрезаны. Пройдена визуальная проверка соседних экранов, кнопок от 48 px и длинных формул без горизонтальной прокрутки всей страницы.
