# Асинхронная передача и интеграция

19.11.2026. **Спецификация для реализации, не отчет о готовом пилоте.** Работа идет через GitHub, коммиты и [HANDOFF_TEMPLATE](../HANDOFF_TEMPLATE.md); синхронные встречи не требуются. Календарная дата рабочей сессии не назначена; часы ниже — контрольные точки согласованной сессии. Границы файлов — [MODULE_BOUNDARIES](MODULE_BOUNDARIES.md), gate совместимости — [COMPATIBILITY](COMPATIBILITY.md).

## Ветки и источник истины

Одна ветка сборки — `integration/pilot-local`. Рабочие ветки — `work/application`, `work/processing`, `work/release`, каждая создается от опубликованного baseline integration. Эти имена являются планом: документ не создает ветки и не выполняет push. До старта в HANDOFF записываются фактические remote, baseline commit, contract commit и исходный SHA. Нельзя подменять integration текущим main неизвестной ревизии.

До B4 слияниями bootstrap и ранней интеграции управляет application; после однократной передачи в 18:00 интегратор release последовательно сливает небольшие PR в integration. B1 фиксирует совместимый baseline и стабильные hooks, но не меняет владельца main/router/Compose/общих конфигов. Соседние ветки обновляются от integration, а не выборочным копированием файлов. PR содержит список затронутых путей, contract version, проверенные команды и doc-impact. В GitHub размещаются только безопасные код/fixtures/отчеты, доступы передаются вне Git. Настоящий бюджетный или live smoke не входит в стандартный CI.

Каждое направление поддерживает `planning/<направление>/HANDOFF.md` в своей ветке. Минимум состояния: `status` (planned/in_progress/ready/blocked), branch+commit, source/contract/baseline SHA, завершенные пункты TASKS/ACCEPTANCE, выполненные команды с результатами, непроверенное, точные зависимости и блокеры. После merge commit интеграции и результат общего smoke записывает application до B4, затем release в `docs/pilot/INTEGRATION_STATE.md`. Ссылка на PR без commit и команд не считается передачей.

B1a/B1b разрабатываются параллельно после B0 на одной основе: application не ждет полной аналитики, processing не ждет экранов. До B1b CRUD использует согласованные сигнатуры и явные fixtures; это не объявляется рабочим сохранением. Если B0 или B1 не пройден, фиксируется конкретный блокер и исправляется ранний вход, а отсутствие основы не переносится молча на 18:00. Контроль около 14:00 — проверка опубликованных артефактов, не обязательная встреча.

Ранние аккаунты обеспечивает application через `app/pilot/operations/create_fixture_accounts.py` и общий auth processing; seed готов до B1, отдельная работа release до 18:00 не является зависимостью. Account seed, его `operations/__init__.py` и все общие entrypoint/config передаются release один раз на B4 в 18:00. До B1 application объявляет hooks подключения, processing предоставляет импортируемые route-модули/worker entrypoint; поэтапная разработка содержимого не ломает запуск. Processing не правит main/router, application поддерживает их до B4. Release после 18:00 доводит операторские скрипты и применяет локальную паузу через CLI; новых HTTP admin endpoints или роли operator не вводится.

В B4 обязательны API smoke `begin-completion → ожидание/оценки → finalize → AnalyticsJob → сохраненная summary`, повтор finalize без дубля, failed analytics + retry, смена отзыва + stale/refresh и поздний ответ старого snapshot. Наличие prompt/schema без worker-пути и сохраненного результата не закрывает передачу. Подставной transport обязателен для воспроизводимости и обозначается в отчете; живое качество модели им не подтверждается.

## Слияние и блокеры

1. Автор публикует небольшой commit/PR и обновляет свой HANDOFF, сохраняя чужие изменения. Публикация выполняется в пределах уже порученной работы и разрешенного репозитория; повторное разрешение на ту же передачу не требуется. Этот протокол не разрешает отдельный серверный выпуск, публикацию школьных данных или изменение upstream.
2. Интегратор сверяет исходный baseline, contract version и владельцев путей. Конфликт общих файлов исправляет текущий единственный владелец, а не оба автора независимо.
3. Выполняются доступные gate из COMPATIBILITY; после merge — затронутый API smoke на integration. Прохождение unit-теста ветки не заменяет совместный запуск.
4. В `INTEGRATION_STATE.md` записываются merge commit, команды, результат и открытые ограничения. При несовместимости merge не объявляется успешным; исправление выполняется новым небольшим commit без скрытого изменения контракта.

Формат блокера: `BLK-<application|processing|release>-NN`, severity, commit/контракт, точная команда/fixture/HTTP, фактический и ожидаемый ответ, владелец исправления, затронутые сценарии. `blocked` означает конкретно невозможный следующий шаг, а не общую сложность. Для дефекта известного контракта интегратор может сразу внести воспроизводимое исправление с тестом; согласие автора не является зависимостью. Новое продуктовое поведение передается владельцу продукта через координатора. Молчание не меняет продукт или контракт.

Вечером release не ожидает возвращения автора processing: использует переданный commit, исправляет дефекты по frozen contract и ведет журнал. Если отсутствует обязательная функция, отмечает невыполненную приемку и восстанавливает ее по ТЗ; не подменяет ее статическим успехом и не объявляет отсутствующее ядро плановой доработкой вечера.

## Фиксация результата

К 21:00 release сохраняет commit локального кандидата, contract/source SHA, режим transport, точные команды запуска и выполненную матрицу приемки. Для каждого пункта — pass/fail/not_run и граница проверки; отдельные failed/not_run не скрываются общей фразой «сборка готова». Моки, эмуляция телефона, live API, реальное устройство, сервер и самостоятельная работа учителя — разные факты. Deploy/внешний доступ требуют отдельной задачи и не входят в локальный результат.

## Staff без ранней зависимости

До B4 application подключает только существующие auth/application/processing/events routers; отсутствующий staff router/UI не импортируется. Ранние auth/asset/history ACL реализуют владельцы app/processing и проверяются до передачи. listStaffChecks/getStaffCheck и полный staff UI создает release в REL-04 после B4. src/App.tsx/src/main.tsx являются bootstrap entrypoint: application до B4, затем release, вместе с main/router/Compose. Application после B4 продолжает teacher-компоненты, не правит принятые shell entrypoint. Функция места подключения не является fake-success staff endpoint; неожиданные ImportError не скрываются.
