# Контракт AI-сводки класса v1

19.11.2026. Спецификация и офлайн-проверки для реализации. **Реализован runtime и выполнен разрешенный text-only live smoke v1**: [результаты/ограничения](../../processing/RUNTIME_REPORT.md). Проверенный checker фотографий не меняется. Основания: R83/R84/R86, [формулы](../../../SUMMARY_METRICS.md), [общий API](../API_CONTRACT.md).

## Вход и запуск

Окончательное согласие учителя атомарно фиксирует состав и создает AnalyticsSnapshot/AnalyticsJob. Worker передает JSON из [input.schema.json](input.schema.json) текстом в отдельном запросе LLM с [prompt-v1.txt](prompt-v1.txt) и структурированным ответом по [result.schema.json](result.schema.json). Фотографии повторно не отправляются. GET summary только читает состояние.

Вход содержит актуальные задачи/разборы и отзывы, а не все исторические попытки. `analysis` — неизмененная Task из frozen checker; wrapper task_id и analysis_id принадлежат приложению. Имена учеников не используются. Комментарии, фото, provider ID, стоимость и служебные логи в модельный snapshot не входят: они сохраняются отдельно для поддержки. Поэтому изменение только комментария не меняет аналитическую data_revision.

`unresolved_bundles` — число актуальных отправленных входов этой тетради без пригодного набора задач: отказ, failed/skipped или валидный, но пустой Report. Явно удаленные задачи не превращают остаток старого набора в такой отказ; у пустой после удаления тетради tasks=[] и unresolved_bundles=0. Неотправленные непустые draft разрешаются до финала. Сервер собирает snapshot из БД, не доверяет этому числу от клиента.

Смена состояния отзыва изменяет data_revision и делает предыдущую сводку неактуальной. `retry` допустим после безопасного failed при stale=false и использует тот же снимок. `refresh` после смены основания создает новый снимок/Job; старый результат не подменяет текущий. Обе операции явные и идемпотентные, чтение не создает запрос. UI использует серверные can_retry/can_refresh: устаревшее гарантированно неотправленное задание можно атомарно заменить, а running/unknown требуют завершения либо сверки. Состав после финала не открывается заново. Детальный lifecycle и статусы — в API_CONTRACT.

## Поля и их потребители

| Поле | Зачем нужно |
|---|---|
| input.snapshot_id/check_id/data_revision | Привязка Job, сохраненного входа и результата к точному состоянию; диагностика старого ответа |
| input.notebook_id | Границы условной работы и знаменатель среднего |
| input.unresolved_bundles | Защита от ложного итога «без ошибок» при failed/пустом входе |
| input.task_id/analysis_id/review_state/analysis | Трассировка, актуальное согласие и источник правила/первой ошибки; source ID модели не используется вместо Task ID |
| output.schema_version | Проверка версии строгого формата |
| output.notebooks.total/with_errors/without_errors/partial/empty | Число работ и различимые группы качества/полноты в итоговом экране |
| output.average_errors_per_notebook | Среднее по полностью подтвержденным непустым работам; null при нулевом знаменателе |
| output.incomplete_tasks | Отдельная нейтральная отметка о подтвержденных незавершенных решениях |
| output.disputed_tasks/unassessed_tasks | Отдельный показ спорных выводов и отсутствующего математического результата; показатели могут пересекаться |
| output.top_errors[].rule/task_ids | До трех смысловых групп правил, частота через длину списка и проверяемые ссылки на задачи |

Не добавляем score/confidence, проценты качества, персональные рекомендации, итоговые оценки, полный текст решения, обязательные rule_id и повторное поле count. Знаменатель среднего доступен как with_errors+without_errors. UI форматирует среднее, например до одного десятичного знака; исходное число проверяется с абсолютной точностью 0.000001.

## Проверка результата

`validate_pair(snapshot, result)` из [validate.py](validate.py) проверяет строгую схему, уникальность и допустимость ID, согласованность разборов, точные количественные инварианты и знаменатель, порядок частот и ссылки топа только на подтвержденные математические ошибки. Частичная тетрадь не входит в среднее, но ее подтвержденная ошибочная задача может войти в топ. Незавершенность/omitted_steps сами по себе не создают ошибку.

Этот валидатор **не генерирует сводку и не классифицирует правила**. Группировку и итоговый JSON создает LLM. Проверка арифметики не заменяет генерацию детерминированным агрегатором. Семантическую корректность группировки нельзя доказать одной JSON Schema: в приемке требуется сравнить смысл правил и включенные задачи. Если ошибок больше трех, отсутствие более частой смысловой группы также требует качественной сверки. При ошибке структуры/инвариантов результат не чинится и не публикуется частично как успешный.

## Перенос в обработчик

Использовать тот же закрепленный model/provider и серверный transport, что для checker; новый вызов содержит system prompt и user JSON, без image parts. Нельзя вызывать frozen PolzaAdapter.analyze для аналитики, подменяя его checker: вынести общий HTTP transport/диагностику в отдельный модуль, а builders и схемы двух типов Job сохранить раздельно. Общая очередь, финансовый резерв и максимум один автоповтор временного технического сбоя применяются к обоим типам Job.

Исходный технический профиль для интеграции — reasoning medium, потолок 25 000 completion tokens, connect 15 s и phase timeout 300 s, как текущая reference-рекомендация checker. На этапе подготовки это был инженерный стартовый профиль; теперь отдельный text-only smoke записан в runtime-отчете. Он не подтверждает photo checker или школьные работы. Размер задания — снимок до обычного согласованного масштаба 30 тетрадей по 3–5 задач; отдельной видимой учителю квоты не вводим. Цена/таймаут/отказ по токенам логируются; length и нарушение JSON/инвариантов не превращаются в частичную сводку. Неизвестная стоимость не равна нулю. Автоповтор не применяется к неверной схеме/арифметике или исчерпанному cap как к временному сетевому сбою.

## Офлайн-приемка пакета

Из этого каталога при установленных jsonschema4 и pytest:

```text
python validate.py
python -m pytest tests -q
```

[Манифест](fixtures/manifest.json) содержит четыре самостоятельных примера: числовой oracle с четырьмя тетрадями и средним 0,5; нулевой знаменатель; mixed Report с неоценимой задачей; объединение синонимичных формулировок. Использованы dev-Task из сохраненных ответов checker и явно обозначенные синтетические варианты. Это ожидаемые контрактные примеры, не ответы нового живого запроса аналитики.

19.11.2026 выполнено: четыре пары fixtures проходят, **15 офлайн-тестов проходят**. Это доказательство валидатора/примеров, не качества нового промпта на модели. Реальный контрольный запрос выполнен отдельно при реализации: small и class30 прошли числовую и смысловую проверку; детали/cost/latency и потерянная первая попытка в runtime-отчете.
