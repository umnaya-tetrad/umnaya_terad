# Общий пакет реализации пилота

Версия 1 · 19.11.2026. Этот пакет задает одни данные, операции, тексты и правила взаимодействия для трех направлений. **Это спецификация и офлайн-проверки. Приложение реализовано; актуальные результаты его локальной проверки и ограничения ведутся отдельно в [CURRENT_STATE](../../../CURRENT_STATE.md) и [RELEASE_REPORT](../../../../docs/pilot/RELEASE_REPORT.md).** Продуктовые решения R01–R86 находятся в [DECISIONS.md](../../DECISIONS.md). Уточнение статуса 20.11.2026 не меняет версии или frozen-состав пакета.

## Читать перед своим ТЗ

1. [API_CONTRACT.md](API_CONTRACT.md), [OpenAPI](api/openapi.json) и [доменные схемы](api/schemas/domain.schema.json) — единственные HTTP/DTO-источники. Старый CONTRACT_DRAFT не является альтернативным API.
2. [MODULE_BOUNDARIES.md](MODULE_BOUNDARIES.md) — исходная ревизия, дерево приложения и владельцы файлов. Shared-файл имеет одного владельца; код пилота создается в корне umnaya_terad, источники остаются отдельными.
3. [MOBILE_UX.md](MOBILE_UX.md), [ux-flows.md](ux-flows.md), [ux-copy.json](ux-copy.json) — экраны, условия действий и короткие тексты для мобильного интерфейса. Не переносить служебные пояснения MD в продукт.
4. [analytics/README.md](analytics/README.md) — отдельный вход, промпт и схема итоговой LLM-сводки. Точный checker фотографий сохраняется в [ai/](../../ai/README.md).
5. [COMPATIBILITY.md](COMPATIBILITY.md) и [HANDOFF_PROTOCOL.md](HANDOFF_PROTOCOL.md) — проверки, однозначная передача через GitHub/HANDOFF, ранний bootstrap, полное ядро к 17:00 и передача до 18:00; интегратор выпуска ведет окончательную локальную сборку к 21:00.

После общего пакета читать только свое ТЗ: [application](../application/README.md), [processing](../processing/README.md) или [release](../release/README.md). Интегратор читает передачи всех направлений. Индивидуальные TASKS/ACCEPTANCE не могут независимо переопределить API или frozen prompt.

Конфигурация и режимы — [LOCAL_ENV.md](LOCAL_ENV.md): один PILOT_TRANSPORT для backend и frontend, явный fixture, polza без автоподмены, единая граница фото и сохраненные исходные имена настроек сессии.

## Одна команда проверки совместимости

Из корня репозитория в отдельном dev-окружении:

```text
python -m pip install -r project-context/pilot/planning/shared/requirements.txt
python project-context/pilot/planning/shared/check_shared.py
```

Команда проверяет байтовые хеши frozen checker, схемы/реальные dev-примеры, соответствие коротких текстов их местам показа, формальную структуру OpenAPI, HTTP fixtures, lifecycle-состояния и арифметику/ссылки примеров аналитики, затем негативные контрактные тесты. JSON references разрешаются локально, без запросов к модели/серверу и без оплаты API. Установка dev-зависимостей может обращаться в пакетный реестр; сам gate не выполняет live-запросов.

Зеленый gate означает, что три направления используют совместимые спецификации и примеры. Он не доказывает реализованную авторизацию, реальную съемку, долговечность очереди, live-качество аналитики или работающий Docker Compose. Программные проверки будущего приложения и операторские команды подробно определены в COMPATIBILITY и индивидуальной приемке; они должны быть созданы при реализации.

## Как менять пакет

У HTTP/DTO, checker и analytics собственные версии. Изменение checker запрещено под видом исправления обертки. Для общего API изменение схемы, типов, fixtures, UX, тестов и затронутых ТЗ выполняется в одном согласованном изменении. Интегратор может исправлять реализацию любого модуля в рамках зафиксированного контракта с записью проверок; новое поведение или несовместимый API не считаются обычным исправлением.

Неиспользуемые поля, отдельная роль администратора, публичная регистрация, учительские квоты, confidence/rule_id, новые сервисы и новые продуктовые функции не добавляются без основания. Поддержка остается read-only; ручная пауза выполняется локальной привилегированной командой, без отдельного HTTP admin API.

Статус независимого ревью и проверок фиксируется в [SHARED_REVIEW.md](SHARED_REVIEW.md); оно не заменяет последующее совместное ревью трех подробных ТЗ. Код, платные прогоны, серверный выпуск и апробация имеют отдельные результаты приемки.
