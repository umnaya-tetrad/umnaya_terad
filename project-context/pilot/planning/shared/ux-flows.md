# Потоки и привязка текстов мобильного пилота

19.11.2026 · спецификация для реализации, без готового интерфейса. Вместе с [MOBILE_UX](MOBILE_UX.md), [ux-copy.json](ux-copy.json) и [API_CONTRACT](API_CONTRACT.md). Здесь перечислены все используемые copy ID и действия; английские состояния и HTTP-маршруты предназначены разработчику, на экран учителя не выводятся. Все маршруты ниже имеют префикс `/api`. Имена отдельных полей DTO сверяются с контрактом, а не угадываются по тексту сообщения.

## Правила каталога

`messages` – конечный минимальный каталог строк этого потока; `placeholders` описывает параметры только тех строк, где они есть. Ключи не являются видимыми текстами. Динамические название проверки, положение задачи (`locator`), формулы, пояснения и названия правил приходят из разрешенного API; отдельными copy ID для каждого математического примера не становятся. Подставляем только текст, без HTML. LaTeX из frozen checker разбирается из JSON один раз и передается математическому рендереру без ручного повторного unescape. Серверные traceback, коды, модель, деньги, ID и revision на экран не попадают.

Неназначенных действий нет: если в текущем состоянии нет разрешенной операции, соответствующая кнопка не показывается либо явно недоступна с причиной. Переход в интерфейсе ничего не подтверждает. Для мутаций существующей проверки используются общая check revision, `If-Match` и `Idempotency-Key`; создание проверки требует только ключ, auth/events используют свои формы по контракту. Повтор после потери ответа использует тот же ключ. Значения `can_finalize`, `can_retry` и `can_refresh` определяет сервер, клиент их не вычисляет из таймера или одного названия состояния.

## S00. Общая навигация и ошибки

| Copy ID | Где и когда | Действие / результат |
|---|---|---|

| `common.save` | Комментарий к отзыву, когда текст изменен | PUT review с текущим analysis_id и прежним state; пустой текст допустим |
| `common.loading` | Первая загрузка истории/деталей | Временный статус до ответа; не обозначает активную обработку ИИ |

| `common.more` | Список проверок/раздел команды, если API возвращает следующую страницу | GET следующей страницы с тем же фильтром, добавить строки без повторения уже показанных |
| `common.conflict` | Ответ 409 при отзыве/составе/финале | Убрать устаревшее действие, оставить введенный комментарий локально; показать refresh |
| `common.network` | Связь потеряна при чтении/передаче | Оставить контекст, доступное повторное исходное действие после восстановления связи; серверная принятая обработка продолжается |
| `common.unavailable` | Материал недоступен/удален/нет доступа | Показать back к истории; не раскрывать существование чужих материалов |
| `common.session_expired` | Ответ 401 | Перейти на S01, после входа восстановить разрешенный контекст; не отправлять формы автоматически |
| `common.save_failed` | Не подтверждено изменение отзыва/комментария | Сохраненное серверное состояние остается отмеченным; повтор – исходная agree/disagree/save, без ложного успеха |

На время mutation блокируем только это повторное действие. После потери ответа сначала сверяем GET: уже принятое не создается второй раз. Поля и кнопки не получают фокус от фонового polling. Несохраненный локальный снимок не обозначается сохраненным.

## S03. Проверка и список тетрадей

Детали текущей проверки и polling получают GET `/checks/{check_id}`. Notebook.number назначает сервер монотонно, без переиспользования удаленных номеров; check.notebook подставляет его напрямую, без парсинга строки. Поля ввода и редактирования названия тетради нет. POST создания тетради не имеет body. Переименования проверки тоже нет: title задается только при создании.

| Copy ID | Показ | Действие / результат |
|---|---|---|
| `check.notebooks`, `check.notebook` | Заголовок списка и условные названия | Строка тетради → ее материалы S04/S06; `number` не ФИО и не постоянный профиль ученика |
| `check.task` | Заголовок каждой задачи в тетради/очереди результатов | Открыть конкретный TaskAnalysis, не задачу с тем же номером в другой тетради |
| `check.add_notebook` | editing/review | POST `/checks/{check_id}/notebooks` → S04; finalized скрывает действие |
| `check.ready_count`, `check.open_ready` | Готовые разборы доступны независимо от pending | Открыть первую доступную карточку S06; очередь по готовности, с номерами исходных тетрадей |
| `check.finish` | editing/review, отдельное действие всей проверки | POST `/checks/{check_id}/begin-completion` → S09; не создает AnalyticsJob, не меняет отзывы |
| `check.summary` | finalized | GET `/checks/{check_id}/summary` → S10; чтение не запускает запрос модели |
| `check.delete` | Учителю, в том числе finalized | Диалог S08 удаления всей проверки |
| `notebook.delete` | Только editing/review в меню конкретной тетради | Диалог S08; после финала отсутствует |

Операционные состояния видны в строках комплектов. Не выводим общий математический нулевой итог до подтверждений. Pending комплект не может выдать «пустую тетрадь без ошибок».

## S04. Камера, галерея, черновик и отправка

| Copy ID | Показ | Действие / результат |
|---|---|---|
| `notebook.empty`, `capture.hint` | Пустой комплект/первая съемка | Указывает границу тетради и совместного продолжения |
| `capture.camera` | Выбор источника | Камера браузера/системный захват; снимок → текущий draft |
| `capture.gallery` | Выбор источника, в том числе после запрета камеры | Выбрать фотографии; их порядок явно показан до отправки |
| `capture.denied` | Камера не разрешена/недоступна | Остается доступна gallery; нет запроса на доступ к чужим приложениям |
| `capture.preview`, `capture.photo` | Предпросмотр текущего комплекта | Все миниатюры в порядке отправки; открыть выбранную фотографию; заменить оставляет позицию, добавление идет в конец |
| `capture.add` | Есть хотя бы одно фото, до отправки | Открыть camera/gallery, добавить продолжение в тот же draft, не отправлять |
| `capture.replace` | У выбранного фото draft | Повторно выбрать camera/gallery; POST нового фото, DELETE прежней ссылки и PATCH порядка draft по правилам ниже. У отправленного комплекта сначала S08 replace |
| `capture.remove` | У выбранного фото draft | S08 delete.photo, затем DELETE `/input-versions/{input_version_id}/photos/{photo_id}`; остальные фото остаются |
| `capture.uploading` | POST `/input-versions/{input_version_id}/photos`, сервер еще не подтвердил | Отправки временно недоступны; сообщение не означает обработку моделью |
| `capture.file_error` | Невалидный/непригодный для передачи файл | Остальные сохраненные фото не теряются; camera/gallery для другого файла |
| `capture.submit_stay` | Есть сохраненные фото, нет активной передачи | POST `/bundles/{bundle_id}/submit` с input_version_id; после 202 новый пустой draft той же тетради |
| `capture.submit_next` | Те же условия, полная подпись в две строки | Тот же submit; после 202 открыть следующую тетрадь, при необходимости создать; без ожидания checker |
| `capture.accepted` | Только после надежного приема submit | Краткий ненавязчивый статус; принятая работа продолжится при закрытии |
| `notebook.next` | В пустом draft или при просмотре готовых материалов | Перейти к следующей тетради без submit; если draft непустой, сначала unsent |
| `capture.unsent` | Попытка уйти с непустым draft / блокер S09 | Остаться и отправить одной из двух кнопок либо discard; отмена сохраняет draft |
| `capture.discard` | В контексте непустого неотправленного комплекта | S08 delete.draft, затем DELETE `/input-versions/{input_version_id}`; не удаляет уже отправленные независимые комплекты |

Новый независимый комплект создается POST `/notebooks/{notebook_id}/bundles`: сервер сразу дает Bundle с пустым draft, отдельный запрос создания InputVersion для него не нужен. Серверный draft и локальный еще не переданный файл различаются. После submit следующая съемка создает новый Bundle, а предыдущий sealed input не меняется. Пустой draft не отправляется. Отправленный комплект не получает «добавление продолжения» задним числом: изменение общего входа – S08 replace и новая версия.

Замена одного фото draft – последовательность POST `/input-versions/{input_version_id}/photos` нового файла, DELETE `/input-versions/{input_version_id}/photos/{photo_id}` старой ссылки, PATCH `/input-versions/{input_version_id}` с полным `photo_ids` в желаемом порядке. Каждый следующий запрос использует check_revision предыдущего Mutation. При сбое между шагами GET восстанавливает фактические фото; интерфейс не заявляет атомарную замену и не отправляет непроверенный порядок. Sealed вход и прежние отзывы от этих действий не меняются. Фото открывается приватным GET `/assets/{photo_id}`.

## S05. Фоновая обработка и окончательная неудача

| Состояние API | Copy ID | Доступные действия |
|---|---|---|
| Job queued/running | `job.pending` | Работать с другими комплектами, смотреть готовое; GET деталей обновляет состояния |
| Job retry_wait | `job.retry_wait` | Ожидать единственный автоматический повтор временного сбоя; ручной повтор одновременно недоступен |
| Job failed | `job.failed` | retry при can_retry, изменить фото до финала, skip |
| Job succeeded, Report.status=uncheckable | `job.uncheckable` | Причина по S07, retry при can_retry, изменить фото до финала, skip всего комплекта |
| Job blocked | `job.blocked` | Другие тетради/возврат/явный skip; retry только при can_retry, без учительского управления деньгами |
| Job unknown | `job.unknown` | Продолжить другое/вернуться/явный skip; не делать новый платный запрос до разрешения сервером |
| Неудачный/uncheckable или mixed комплект, retry разрешен | `job.retry` | Сначала предупреждение S08 об общем комплекте, затем POST `/bundles/{bundle_id}/retry`; новая попытка того же комплекта, не новая тетрадь/задача; checker retry после финала запрещен |
| failed, uncheckable, blocked либо unknown, не пропущен | `job.skip` | POST `/bundles/{bundle_id}/skip`; сохраняет материалы/историю и разрешает дальнейшее завершение; публикация позднего ответа подавляется |
| Комплект явно пропущен | `job.skipped` | Не отображать как успешную проверку; до финала при разрешении сервера можно вернуться к retry/изменению фото |

Успешный Job имеет state=succeeded; пригодность его Report определяется отдельно в S06/S07. `cancelled/superseded` не являются отдельными кнопками/ошибками текущей задачи; явный skip отображается job.skipped. После GET показывается действующая версия; старые попытки не возвращают старые отзывы/удаленные материалы. Нельзя автоматически показать retry для unknown только по прошедшим секундам. При can_retry=true неизвестный исход уже разрешен сервером: вместо фразы unknown с запретом повтора показывается нейтральная окончательная неудача `job.failed` и retry. Пропуск unknown не означает, что внешний запрос не выполнялся: технический исход команда уточняет отдельно, без нового запроса от учителя.

## S06. Готовый разбор и отзыв по задаче

| Copy ID | Условие и источник | Действие / результат |
|---|---|---|
| `result.title` | Готовый TaskAnalysis, рядом check.notebook/check.task | Контекст сохраняется при просмотре других фото |
| `result.enlarge` | У фото из photo_indices этой задачи | Полноэкранное увеличение; несколько фото с capture.photo, common.close возвращает в карточку |
| `result.condition` | Непустое condition | Математическая запись из текущего TaskAnalysis |
| `result.lines` | Непустое evidence | До четырех исходных строк с номерами фото; без выдуманного полного OCR |
| `result.error_found` | result=first_error_found | Первая ошибка ученика, не красный отзыв об ИИ |
| `result.correct` | result=all_steps_correct | Корректность видимых записанных шагов, независимо от завершенности |
| `result.incomplete` | completeness=incomplete | Отдельно + completeness_note при наличии; не добавляет ошибку |
| `result.completeness_unknown` | completeness=unknown | Не объявлять задачу завершенной; available note остается пояснением |
| `result.first_error`, `result.rule`, `result.explanation`, `result.corrected` | first_error не null | wrong_latex, raw rule, explanation, corrected_latex соответственно; не создаем rule_id/confidence |
| `review.help` | Перед кнопками оценки ИИ | Разъясняет смысл двух кнопок на каждой карточке |
| `review.unreviewed` | Review отсутствует (null) | Никакого автоматического согласия по просмотру |
| `review.agree` | Пригодная актуальная задача, учитель | Зеленая галочка; PUT `/tasks/{task_id}/review`, state=confirmed, конкретный analysis_id; не меняет соседние задачи |
| `review.disagree` | Та же доступность | Красная; тот же PUT со state=system_error; немедленно сохраняет отметку и не требует комментария, не запускает checker |
| `review.confirmed`, `review.system_error` | Только подтвержденное сервером состояние | Текстовая отметка выбранного состояния, обе кнопки доступны для изменения, в том числе после финала |
| `review.comment_label`, `review.comment_placeholder` | У сохраненного отзыва | Поле необязательно, не редактор OCR; common.save сохраняет comment с тем же state |
| `review.saved` | Успех PUT | Краткое подтверждение; не показывать при 409/сбое/несохраненном тексте |
| `review.next` | Есть следующая доступная карточка | Открыть следующую готовую задачу, текущей не ставить автоматический отзыв; если следующей нет, кнопка отсутствует |
| `review.report` | Текущий отзыв сохранен, `completion.unreviewed_tasks=0` | Перейти к существующему экрану завершения и формирования отчета; после финала открыть сводку. Остальные blockers и окончательное согласие сохраняются, формирование аналитики не запускается автоматически |
| `result.change_photos` | Только до финала, в меню контекста комплекта | S08 replace; общий вход и все затронутые задачи, а не только эта карточка |
| `task.delete` | Только до финала | Диалог S08 delete.task; общий photo asset не удаляется |

Смена только comment после финала оставляет summary актуальной; смена state делает ее stale. Отзыв не изменяет исходный математический вывод. Повторные нажатия сохраненного выбора не создают новых подтверждений/задач. Нет автоперехода после согласия: учитель может дописать замечание на бумаге и затем сам нажать next.

## S07. Неоценимая задача и смешанный Report

| Copy ID | Где | Действие / результат |
|---|---|---|
| `result.no_result` | task.result=not_assessed | Фото/положение и понятная причина, без математического нуля; whole Report.uncheckable использует job.uncheckable |
| `result.unreadable` | Причина явно сообщает нечитаемость | Предложение переснять свою страницу/skip |
| `result.missing_condition` | Причина явно сообщает нехватку условия | Переснять решение с достаточными данными либо skip; нет загрузки отдельного условия |
| `result.unsupported` | Неподдерживаемый или иной семантический отказ | Короткое объяснение; безопасный task.uncheckable_reason/message можно показать ниже, если он относится к задаче и не содержит технических деталей |
| `task.skip` | Только not_assessed, skipped=false | POST `/tasks/{task_id}/skip` с analysis_id; разрешить эту задачу, а не весь Bundle |
| `task.skipped` | not_assessed, skipped=true | Остается видимой, не получает review=confirmed и не удаляется |

Нет неподтвержденного детерминированного классификатора свободных причин по ключевым словам: если тип не известен надежно, показывается общий result.no_result + безопасная исходная причина, а не догадка о нечитаемости/условии. Эти copy ID – текстовые варианты, не новые enum checker.

Для not_assessed доступны фотографии, change_photos и retry общего комплекта при разрешении сервера до финала. Зеленая/красная кнопка отсутствует. В mixed Report соседняя all_steps_correct/first_error_found использует S06 и сохраняет свой отзыв; пропуск not_assessed разрешает completion отдельно. Report.status=uncheckable относится к комплекту S05 и использует job.skip. Повтор/замена общего входа предупреждает о последствиях для соседней уже подтвержденной задачи.

| Copy ID | Показ | Действие / результат |

| `replace.confirm` | Диалог замены | POST `/bundles/{bundle_id}/versions` с photo_ids текущего sealed входа в исходном порядке, открыть replacement draft; создание/отмена draft сохраняют отзывы. Согласия снимаются только при submit нового входа, не переносятся по похожести |
| `delete.title` | Любое удаление | Заголовок + ровно один объектный текст ниже |
| `delete.photo` | Фото draft | Показать номер конкретного фото |
| `delete.draft` | Весь неотправленный комплект | Явно предупредить про все его фото |

При delete.task используется DELETE `/tasks/{task_id}`, при delete.notebook – DELETE `/notebooks/{notebook_id}`, при delete.check – DELETE `/checks/{check_id}`. Другие маршруты указаны в S04. После финала доступны только delete.check и чтение; нельзя добраться до удаления состава прямой ссылкой или старой открытой вкладкой. Серверная ошибка не показывает ложный успех. Подтвержденное удаление не имеет кнопки восстановления.

## S09. Первый шаг завершения, ожидание и финальное действие

| Copy ID | Условие | Действие / результат |
|---|---|---|
| `finish.title` | phase=review после begin-completion | Никаких изменений состава/отзывов от самого открытия |
| `finish.pending` | completion.pending_jobs>0 | Показать количество и текущие состояния S05; готовые разборы доступны через check.open_ready |
| `finish.unreviewed` | completion.unreviewed_tasks>0 | check.open_ready открывает первый пригодный разбор без отзыва; review null остается блокером |
| `finish.unresolved` | completion.unresolved_tasks>0 либо unresolved_bundles>0 | finish.open_materials ведет к первому из них, S05/S07; задачи и комплекты не складываются в ложное количество задач |
| `finish.empty` | can_finalize=false, все счетчики completion равны 0 и нет ни одного активного sealed input | Рядом capture.camera/capture.gallery ведут к фото первой тетради по S04; при отсутствии тетрадей сначала POST создания первой тетради без body. Нужно отправить комплект, пустую проверку не финализируем |
| `finish.drafts` | Непустые draft | finish.open_materials ведет к фото S04, явно submit либо discard |
| `finish.open_materials` | Всегда до окончательного завершения | Вернуться к редактируемым тетрадям, сохраняя phase=review; отдельная фаза «reopen» не вводится |
| `finish.finalize` | Только серверное can_finalize=true | Открыть диалог окончательного согласия; не массовая запись отзывов |
| `finish.confirm_title`, `finish.confirm_body` | Финальный диалог | Последствия фиксации состава; отзывы/комментарии продолжают редактироваться |
| `finish.excluded` | Финальный диалог, включая нулевые счетчики | Явно показать отдельно system_error, пропущенные задачи и пропущенные комплекты; они исключены из подтвержденной математической аналитики |
| `finish.confirm` | Подтверждение диалога | POST `/checks/{check_id}/finalize` с актуальной revision, атомарно один snapshot+AnalyticsJob; ответ → S10 |
| `finish.finalizing` | Пока finalize не подтвержден | Повторный клик недоступен; при потере ответа GET состояния и повтор с тем же ключом |

Красная оценка system_error считается явным отзывом и не мешает финалу сама по себе. Она никогда не превращается в confirmed. Неоценимое без явного skip блокирует, явное skip разрешает. Еще не завершенные задания/непустые draft/пригодные задачи без отзыва блокируют. После редактирования сервер пересчитывает completion. При 409 даже ранее доступный finalize не исполняется по старому can_finalize.

Проверка без подтвержденных пригодных разборов не получает выдуманный нулевой итог: если сервер допускает финал разрешенного состава, S10 показывает summary.no_data. GET/переход назад не создают AnalyticsJob. Само начало завершения не блокирует съемку, замену и удаление до финального подтверждения.

Учителю показывается только выбранная текущая сводка. Новый отзыв во время обработки оставляет тот запуск устаревшим; поздний ответ не становится текущим автоматически. Только comment не вызывает stale. При stale+failed доступен только refresh и только при can_refresh=true: retry старого snapshot запрещен. Сервер может разрешить refresh для stale+queued/blocked, если гарантирует, что прежний Job еще не отправлялся; refresh атомарно помечает тот Job superseded и создает актуальный. Клиент не пытается вывести эту безопасность из state: он читает can_refresh. Для running, retry_wait с возможной отправкой и unknown capability false до завершения/сверки. Тогда показываются существующие summary.pending/summary.retry_wait/summary.unknown и недоступная refresh, без нового запроса. Кнопки не обещают изменить состав закрытой проверки.

## Проверочные сценарии передачи

1. Вход → новая проверка → тетрадь → целая страница с несколькими задачами; добавить продолжение вторым фото. До submit одно фото не приравнивается к задаче. После submit_next следующая тетрадь доступна, камера не ждет модель. Готовность второго комплекта раньше первого видна без прерывания съемки.
2. Для E_C01/K01/M06 из ai/examples сверить видимые карточки с описанием в MOBILE_UX: максимум четыре evidence, конкретные photo_indices, первый неверный/исправленный шаг; отдельные отзывы на соседние задачи. Это будущая проверка рендера, не новый запуск LLM.
3. all_steps_correct+incomplete сохраняет ноль первых ошибок и отдельную незавершенность. not_assessed остается без математического вывода. Mixed Report: skip только not_assessed, соседний confirmed остается в топе, тетрадь вне среднего.
4. Временный сбой имеет один автоматический повтор; затем ручные разрешенные действия. Красный отзыв не запускает retry. unknown не имеет автоматического нового запроса. Смена фото общего комплекта снимает затронутые согласия; независимые комплекты сохраняются, поздний старый результат не возвращается.
5. Отмена каждого delete ничего не меняет. Подтверждение удаляет ровно выбранный состав; задача не удаляет соседнее общее фото. Отмена замены не создает новый разбор. Непустой draft не теряется при переходе/завершении.
6. Первый finish → ожидание и review; материалы редактируются. Finalize недоступен с null отзывом/неразрешенным отказом/непустым draft, а также без единого активного sealed входа даже при нулевых счетчиках. system_error и явный skip не становятся confirmed. Финальный клик создает один AnalyticsJob, состав фиксирован, отзывы/комментарии редактируемы.
7. Сводка pending/failed/blocked/unknown не содержит выдуманных чисел. Смена state → stale → явный refresh по can_refresh; comment-only не создает запуск. Retry только по can_retry=true при stale=false; stale+failed не позволяет retry. Stale+queued/blocked может разрешить can_refresh только сервер, running/unknown ждут исхода/сверки. История проверок возвращает к текущему результату; история запусков доступна staff, GET не вызывает LLM. Ноль с ненулевым знаменателем отличается от отсутствия данных.
8. Повторный вход/другое устройство возвращает сохраненные материалы; 409 требует актуализации без молчаливой перезаписи. Staff видит разрешенные материалы, но не может менять отзыв/состав/запуски. При увеличении текста 200% и ширине 320px все действия остаются доступными.

Механическая проверка каталога выполнена: JSON разбирается, все 157 messages ID явно встречаются выше, нет неизвестных ID, набор placeholder в строке равен описанному; все кнопки имеют назначение. 28 уникальных путей и 31 пара HTTP method/path сверены с итоговым OpenAPI; can_refresh и Notebook.number сверены со схемой. Результаты общего офлайн gate записаны в MOBILE_UX. Локальная проверка приложения/доступности, сеть, live LLM и публикация в этой задаче не выполнялись; эта спецификация не заменяет программную приемку.
