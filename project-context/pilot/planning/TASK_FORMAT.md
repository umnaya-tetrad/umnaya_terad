# Формат трех индивидуальных ТЗ

Это единый формат документации задач. Привязка к людям и личные характеристики в файлы не включаются. Рабочие направления: application, processing, release.

В каждой папке обязательны README.md (вход и область), TASKS.md (задачи), ACCEPTANCE.md (тест-кейсы/проверки), HANDOFF.md (текущее фактическое состояние). Источник общих правил — [shared/README.md](shared/README.md). ТЗ не создает альтернативный API.

## Каждая задача

- ID, короткое название, контрольная точка готовности.
- Зачем и основание: R/A-ID, ссылки на общий контракт/UX/модуль.
- Входные зависимости: готовый артефакт/операция/fixture и поставщик; отсутствие встречи не является зависимостью.
- Файлы реализации и исключения владения по MODULE_BOUNDARIES.
- Конкретные действия и выходные артефакты.
- Проверка: сценарий/вход → действие → ожидаемый ответ/сохраненное состояние, команда и ссылка на ACCEPTANCE.
- Definition of Done: проверяемые условия, включая ошибки/версии/права там, где они существенны; нет пункта «все работает» без проверки.

## ACCEPTANCE

Содержит локальные/интеграционные/мобильные проверки с ID, исходными данными, шагами, точным ожидаемым результатом и исполняемой командой либо ручными шагами. Команды будущего приложения помечаются как требуемые к созданию, а не выданные за выполненные. Fixtures и operationId берутся из общего пакета; математический oracle и критерии группировки не подменяются простым совпадением вердикта.

## HANDOFF

Начальное состояние planned. Сделанное записывается только после commit/проверки; неизвестные SHA/результаты не выдумываются. Использовать [шаблон](HANDOFF_TEMPLATE.md) и [протокол](shared/HANDOFF_PROTOCOL.md), указать, какой baseline/контракт/fixtures применены, какие команды прошли и что осталось. Полная передача processing до 18:00 включает доказанный API-путь итоговой аналитики. Release принимает итоговую локальную сборку к 21:00; технический успех подставного transport отдельно от live модели и внешнего выпуска.
