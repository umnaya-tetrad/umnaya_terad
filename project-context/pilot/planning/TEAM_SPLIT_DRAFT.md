# Предложение параллельной разработки локальной версии

19.11.2026. **Черновик для обсуждения, не согласованные индивидуальные ТЗ и не обещание выполнения всей приемки пилота за одну сессию.** Основание: [требования](../PRODUCT.md), [архитектура](../TECHNICAL_PLAN.md), [этапы](../IMPLEMENTATION_PLAN.md), [приемка](../TRIAL_AND_ACCEPTANCE.md). Цель ближайшей сессии — собранная локальная версия к 21:00; внешнее развертывание в эту точку готовности не входит. Календарная дата сессии отдельно не назначена.

Здесь описаны направления работы и результаты, без характеристик участников. Назначения исполнителей и точные объемы будут определены отдельно. Ниже нет новых обязательных функций за пределами требований пилота.

Подтверждены способ передачи через GitHub и файлы состояния, Docker Compose для локального результата и ответственность интегратора локального выпуска за сборку/слияние/блокирующие исправления. Состав подробных ТЗ и версия контракта еще не зафиксированы.

## Рекомендуемые направления

| Направление | Область владения | Что не менять независимо |
|---|---|---|
| Интерфейс и стандартные операции приложения | Мобильный UI входа, списка/истории проверок, тетрадей, съемки комплектов, разборов и отзывов, завершения и сводки; прикладные API создания/чтения и сохранения отзывов по общему контракту | Общую схему данных, семантику версий/завершения, механизм очереди и AI-контракт |
| Ядро обработки и продуктовые контракты | Схема связей/состояний, общие проверки доступа, прием зафиксированного комплекта и Job, worker, подключение готового адаптера, сохранение результата, контракт/промпт отдельной AI-сводки | Публичный API после согласования без уведомления смежных направлений; точный checker без отдельного решения/валидации |
| Локальная сборка и приемка | Воспроизводимый запуск API/worker/PostgreSQL/клиента, миграции и выдаваемые тестовые аккаунты, постоянные volumes, проверка закрытого доступа, восстановление, сквозная регрессия, минимальный закрытый просмотр команды и логи | Семантику продукта и модельные выводы; интегратор вправе исправлять воспроизводимый дефект любого модуля по зафиксированному контракту, записывая diff/проверки; новое поведение или несовместимый контракт требуют отдельного решения |

Типовой CRUD может реализовываться рядом с UI при заранее определенных моделях и общих функциях авторизации. Критичные проверки прав, создание задания и версии входа должны иметь единый контракт и приемочные примеры. Полный backend не выделяется как один неопределенный блок.

## До начала параллельной работы: общий пакет контрактов

1. Направление приложения отвечает за bootstrap: закрепленный исходный commit SmartNoteLanding, раннюю интеграционную ветку, подключение router и первоначальный Compose-запуск. Направление обработки поставляет общие модели/миграции и entrypoint worker. Минимальный API/БД/клиент/worker и тестовая сессия должны запускаться до раннего интеграционного прогона, а не впервые вечером. В локальном источнике уже найдены FastAPI/React, код login/session, миграции и Compose; повторное использование требует проверки текущей ревизии и feature flags. Найденный код не равен готовому учительскому кабинету.
2. Определить владельца каждого модуля, рабочие ветки и порядок небольших интеграций. Избежать независимых изменений одного файла роутов, миграции или общей схемы.
3. До начала реализации согласовать [кандидат API и взаимодействия](CONTRACT_DRAFT.md), затем создать OpenAPI, доменные схемы, типы и fixtures. Сессия, проверка/тетрадь, draft/фото, submit/status/result, отзыв, завершение, аналитика должны иметь однозначную форму. Пока этот пакет не готов, технические ТЗ не считаются готовыми к независимой выдаче.
4. Дать клиенту согласованные fixtures на основе сохраненных [dev-ответов](../ai/README.md), включая ошибку, незавершенность, несколько задач и продолжение. Подмена API предназначена для разработки/автотестов и обозначается явно.
5. Закрыть продуктовые зависимости завершения и аналитики: фиксированный состав R84, двухэтапное завершение R86 (Q50 закрыт), JSON-контракт сводки Q49. Проработку не откладывать до финальной сборки.

## Основная реализация и передача до 18:00

| Направление | Ожидаемый результат |
|---|---|
| Интерфейс и стандартные операции | Проходимые экраны и реальное сохранение проверок/тетрадей/фото/отзывов; камера и галерея, три действия комплекта, polling и состояния ошибок. Список истории и возврат после перезагрузки. UI работает по согласованному API; сначала можно разрабатывать на fixtures |
| Ядро обработки и контракты | К 17:00 завершены прием комплекта, долговечный Job/worker, сохранение результата, отзывы/версии и двухэтапный финал с отдельной AI-сводкой. Адаптер используется без переписывания checker. 17:00–18:00 — исправления и передача: закоммиченный код, тесты, примеры, команды запуска и диагностики. Реализация аналитики не переносится на вечер |
| Общая точка интеграции | Еще до 18:00 выполнить первый путь «вход → проверка → фото → сохраненный Job → результат → отзыв → возврат из истории». Дополнительно до передачи обязателен API smoke завершения и аналитики без зависимости от готового UI: begin-completion → ожидание/оценки → finalize → AnalyticsJob → сохраненная summary; повторный finalize, сбой аналитики и изменение отзыва проверяются отдельно. На промежуточном этапе transport модели допускается подставной с явной пометкой. Первый совместный запуск нельзя переносить на 21:00 |

Контроль без обязательных встреч: результаты контрактных проверок и короткий файл состояния публикуются в рабочих ветках. Около 14:00 проверяется совместимость API/fixtures, около 16:00 — первый путь на общей базе, к 17:00 — функциональная готовность ядра; до 18:00 выполняется передача. Это ориентиры контроля, не гарантированная оценка трудозатрат. Реальные несовпадения фиксируются с воспроизведением и ожидаемым ответом.

## С 18:00 до 21:00

| Направление | Работа после промежуточной сборки |
|---|---|
| Локальная сборка и приемка | Запустить проект в чистом локальном окружении по инструкции, проверить миграции/volumes/аккаунты и отделение API от worker. Проверить две учетные записи, восстановление после закрытия/рестарта, отсутствие двойной отправки, ошибки/повторы и логи. Подключить минимальный закрытый просмотр команды. Повторять приемочные проверки после исправлений |
| Интерфейс и стандартные операции | Подключить оставшиеся реальные endpoints, завершить экран итогов/истории и обработку отказов, исправить дефекты сквозного прогона. Не начинать независимый редизайн |
| Переданный пакет ядра | Используется версия, переданная до 18:00. По известным контрактам исправления может выполнять интегратор совместно с направлением приложения. Новые продуктовые решения и доработка отсутствующей аналитики не являются плановыми вечерними зависимостями |

Интегратор локального выпуска отвечает за сборку, слияние веток и устранение блокирующих дефектов во всех модулях. Работа не требует обязательного синхронного участия автора каждого модуля. Около 20:15 — полная общая сборка; 20:15–21:00 — только исправление блокирующих дефектов, повтор приемки и фиксация результата. Серверный выпуск выполняется отдельным этапом. Эти интервалы — предложение организации работ.

## Проверяемый результат к 21:00

1. Клиент, API, БД и независимый worker запускаются Docker Compose по документированной команде; предусмотрены миграции, тестовые аккаунты, постоянные volumes и healthchecks. Docker доступен на приемочной машине; секретов в Git нет.
2. Выданный аккаунт входит; свои проверки и материалы сохраняются после перезапуска и повторного входа. Два аккаунта не читают чужие материалы.
3. Учитель создает проверку и несколько тетрадей; отправляет страницу с несколькими задачами и комплект с продолжением на двух фото; съемка следующего комплекта не ждет модель.
4. Каждый полученный разбор связан с правильной тетрадью/версией. Двойной клик не создает два задания; временный технический сбой имеет не более одного автоповтора. Закрытие вкладки не отменяет принятый Job.
5. Согласие/ошибка ИИ и комментарий сохраняются; спорное не превращается в подтвержденную математическую ошибку.
6. Первое действие завершения открывает ожидание/просмотр и еще позволяет редактирование; окончательное согласие фиксирует состав согласно R84/R86 (Q50 закрыт). Итоговая аналитика формируется отдельным запросом по согласованному контракту, привязана к актуальным данным и сохраняется в истории.
7. Работает закрытый просмотр команды, есть диагностические логи попыток/времени/стоимости без секретов.

Автотесты используют подставной transport. Проверку реальной моделью учитывать отдельно от интерфейсных тестов и выполнять только в рамках явно выделенного бюджета. Нельзя объявлять подставной ответ подтверждением живой интеграции. Этот план платных вызовов не выполняет и новый бюджет не устанавливает.

## Что предстоит превратить в ТЗ

Для каждого направления: точные файлы/модули, API и модель данных, входные зависимости, сценарии успеха/ошибки, тест-кейсы, Definition of Done, команды проверки и материалы передачи. Особое внимание: завершение с неготовыми/спорными задачами, замена/удаление до фиксации состава, изменяемые отзывы после завершения, snapshot и актуальность аналитики. Данное предложение еще не заменяет эти ТЗ.

## Асинхронная работа и структура ТЗ

- [application/README.md](application/README.md) — приложение и стандартные API.
- [processing/README.md](processing/README.md) — обработка и продуктовые контракты, полный результат передается до 18:00.
- [release/README.md](release/README.md) — локальный выпуск и независимая приемка, ответственность за интеграцию 18:00–21:00.
- [HANDOFF_TEMPLATE.md](HANDOFF_TEMPLATE.md) — формат короткого файла состояния в рабочих ветках.

После фиксации контрактов каждая папка должна содержать TASKS.md, ACCEPTANCE.md, HANDOFF.md с модулями, зависимостями, задачами/подзадачами, промежуточными результатами и DoD. Пока это каркасы ТЗ. Финальную детализацию трех частей нужно проверить независимыми агентами на совпадение контрактов, отсутствие циклических зависимостей, полноту требований и возможность выполнения без истории чата.

GitHub и файлы состояния — согласованный основной канал передачи. До старта определяются рабочая ветка интеграции и правила слияния. Общие контракты/миграции меняются через одного владельца; односторонняя правка маршрута или значения enum запрещена после фиксации версии. Блокер описывается через ID, команду воспроизведения, фактический/ожидаемый ответ и затронутый контракт. Отсутствие ответа коллеги не считается согласованием изменения продукта.

Матрица владения всей приемкой A01–A25 — [COVERAGE_MATRIX.md](COVERAGE_MATRIX.md); итоги предварительного независимого ревью и незакрытые условия фиксации — [REVIEW_NOTES.md](REVIEW_NOTES.md).
