# Предварительный контракт независимой реализации

Версия 0.1 · 19.11.2026. **Техническое предложение для согласования до начала параллельной разработки. Это еще не замороженный OpenAPI и не реализованные endpoint.** Продуктовые основания: R80–R86 в [решениях](../DECISIONS.md). Распределение: [TEAM_SPLIT_DRAFT.md](TEAM_SPLIT_DRAFT.md). Проверенный AI-контракт не меняется: [AI_INTEGRATION.md](../AI_INTEGRATION.md).

## Границы ответственности

1. Клиент формирует упорядоченный комплект фото одной тетради. До ответа модели ему не нужно создавать учебные задачи или знать их число.
2. API сохраняет вход и создает долговечное задание. Worker проверяет комплект одним запросом и сохраняет выделенные задачи. Закрытие браузера и переход к следующей тетради не влияют на обработку.
3. У каждого выделенного результата своя отметка учителя. Общий JSON модели может содержать несколько задач; согласие с одной не подтверждает соседние.
4. Завершение всей проверки двухэтапное. Финальное согласие фиксирует состав и запускает другой тип фонового задания — аналитику по сохраненному JSON.

## Сущности и идентификаторы

| Объект | Минимальная роль |
|---|---|
| Check | Владелец, название, `id`, `revision`, `phase`, время создания; содержит тетради |
| Notebook | `id`, `check_id`, условный номер, порядок; без ФИО |
| Bundle | Постоянный `id`, `notebook_id`, `current_input_version_id`; логическая группа совместных фото |
| InputVersion | Собственный `id`, `bundle_id`, упорядоченные ссылки на фото, revision и `draft/sealed`; единица одного запроса checker |
| Photo | `id`, закрытая выдача через API, порядок; `photo_index` модели считается от 1 внутри конкретной версии |
| Job / Attempt | Тип `page_check/class_analytics`, ID входа/снимка, состояния, поколения/попытки, usage/стоимость |
| BundleAnalysis | Неизменяемый полный Report `page-check/1.2` по версии комплекта |
| Task / TaskAnalysis | ID записи выделенной задачи и ID конкретного ее разбора, не обещание тождества математической задачи после повторного выделения, ссылка на BundleAnalysis и относящиеся фото |
| Review | `task_analysis_id`, `state`, комментарий, `revision`; относится к одному выделенному результату |
| AnalyticsSnapshot / AnalyticsResult | Сохраненный состав и отзывы в момент финала; неизменяемая версия запроса/ответа сводки |

Запись Task имеет устойчивый ID внутри сохраненного поколения результатов; политика замещения поколений при повторной сегментации еще требует фиксации (см. блокирующие инженерные вопросы ниже).

`task_id` из ответа LLM локален внутри этого ответа и не используется как первичный ID приложения. Физические названия таблиц еще предстоит определить; таблица выше задает семантику связей. В API везде возвращаются серверные ID. `analysis_id` в отзыве означает TaskAnalysis, а не общий BundleAnalysis.

## Состояния и данные для UI

`Check.phase`: `editing`, `review`, `finalized`.

- `editing`: можно фотографировать, отправлять и просматривать результаты.
- `review`: первый шаг завершения. Можно ждать обработку, оценивать разборы и менять материалы до окончательного согласия.
- `finalized`: состав закрыт для добавления/замены/удаления отдельных материалов; аналитика может еще выполняться. Финал проверки не равен готовности ее аналитики.

`Job.state`: `queued`, `running`, `retry_wait`, `waiting_funds`, `ready`, `uncheckable`, `failed`, `cancelled`, `superseded`. Активное ожидание не становится математическим отказом. Неопределенный исход запроса хранится отдельно и не ведет к безусловной новой платной попытке.

`Review.state`: `pending`, `agreed`, `system_error`. Поля математической оценки остаются как в checker: `result`, `completeness`, `detail_level`. `system_error` — отзыв о системе, не ошибка ученика.

В деталях проверки сервер возвращает производный блок `completion`:

```json
{
  "pending_jobs": 1,
  "unreviewed_tasks": 2,
  "unresolved_inputs": 0,
  "unsent_drafts": 0,
  "can_finalize": false,
  "blockers": ["processing_pending", "reviews_pending"]
}
```

Это предложение полей UI, не финальная схема. Неотправленные непустые draft требуют явного решения, их нельзя молча терять. Технически неудачные/неоценимые входы имеют явный ручной повтор, пересъемку либо пропуск; вечный спиннер недопустим. Красная отметка является явной оценкой и не превращается в зеленую при финале. Вопросы точного отражения пропущенных элементов входят в детальное ТЗ/Q49; они не требуют изменения checker.

## Операции HTTP — кандидат имен

Общие правила: JSON UTF-8, UUID в виде строк, даты UTC ISO8601; те же server session cookie, что использует приложение. Ключ Polza находится только на сервере. Маршруты авторизации ниже переиспользуют найденный код лендинга; роли и запрет публичной регистрации нужно адаптировать под пилот.

| Операция | Предложенный вход/выход |
|---|---|
| `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session` | Выданный логин/пароль, серверная cookie; UI получает ID и роль без секрета сессии |
| `GET /api/checks`, `POST /api/checks` | История и создание по `title`; проверка сохраняется еще до финала |
| `GET /api/checks/{id}` | Текущее состояние, revision, тетради, комплекты, выделенные задачи/разборы/отзывы, completion и состояние аналитики; используется для восстановления и polling |
| `POST /api/checks/{id}/notebooks` | Создать условную тетрадь; возвратить ID и номер |
| `POST /api/notebooks/{id}/bundles` | Создать пустой draft-комплект |
| `POST /api/bundles/{id}/photos` | Multipart с одним фото, input_version_id, порядок и expected revision; изменение только текущей draft-версии; ответ подтверждает сохраненный Photo |
| `POST /api/bundles/{id}/submit` | Явный input_version_id: зафиксировать все фото текущей draft-версии и создать Job; `202` с идентификаторами |
| `POST /api/bundles/{id}/retry` | Ручной повтор актуального входа после неудачи; не создает новую учебную задачу |
| `POST /api/tasks/{id}/skip` | Явно разрешить not_assessed TaskAnalysis как пропущенный с analysis_id и expected revision, без пропуска соседних задач |
| `POST /api/bundles/{id}/skip` | Явно пропустить неудачный/неоценимый вход, сохранив его историю и отсутствие математического вердикта |
| `GET /api/assets/{id}` | Закрытая выдача фото с проверкой владельца/роли; не публичный статический путь |
| `PUT /api/tasks/{id}/review` | Конкретные `analysis_id`, `state`, `comment`, `expected_review_revision`; отзыв только по выбранной задаче |
| `POST /api/checks/{id}/begin-completion` | Перейти к ожиданию/просмотру, вернуть актуальный completion. Не создает AnalyticsJob |
| `POST /api/checks/{id}/finalize` | Ожидаемая revision и ключ идемпотентности; проверить условия, зафиксировать состав/снимок и создать AnalyticsJob; `202` |
| `GET /api/checks/{id}/summary` | Состояние и сохраненный результат аналитики; чтение само не запускает LLM |
| `DELETE /api/tasks/{id}`, `DELETE /api/bundles/{id}/photos/{photo_id}`, `DELETE /api/notebooks/{id}`, `DELETE /api/checks/{id}` | Проверка прав/версии, подтверждение в UI. Изменения состава запрещены после финала; удаление всей проверки остается отдельным согласованным действием |
| `POST /api/bundles/{id}/versions` | Предлагаемая единая операция подготовки замененного общего входа до финала; точная форма в детальном ТЗ. После изменения снимаются отзывы всех затронутых разборов |
| `GET /api/staff/checks` и детали | Чтение материалов с серверной ролью и аудитом, без изменения отзывов за учителя |
| `POST /api/events` | Пакет событий с ID/временем, дедупликацией; фото и полный текст ответа не копируются в общие события |

У обеих кнопок отправки один submit. «Остаться» либо «перейти к следующей тетради» — клиентское действие после подтвержденного приема; оно не меняет математический запрос. Динамически созданные задачи не отправляются повторно каждая своей кнопкой submit. Если исходное фото общее, повтор/замена относятся к комплекту, а не только к одному фрагменту Report.

## Важные формы сообщений

Пример подтверждения приема, значения ID здесь условные:

```json
{
  "bundle_id": "bundle-example",
  "input_version_id": "input-example",
  "job_id": "job-example",
  "state": "queued",
  "check_revision": 12
}
```

Пример сохранения отзыва:

```json
{
  "analysis_id": "task-analysis-example",
  "state": "system_error",
  "comment": "Неверно распознан знак",
  "expected_review_revision": 0
}
```

Пример безопасного конфликта:

```json
{
  "error": {
    "code": "revision_conflict",
    "message": "Данные изменились. Обновите проверку.",
    "current_revision": 13
  }
}
```

Формы иллюстрируют поля; условные `*-example` не валидные UUID. В итоговых fixtures использовать валидные постоянные тестовые ID и полную JSON-схему. Серверная ошибка не возвращает внутренний traceback, реквизиты окружения или сообщение с ключом.

## Конфликты, повторные действия и фиксация

- Submit/finalize используют сохраняемый клиентом `Idempotency-Key`. Повтор того же ключа с тем же действием возвращает тот же объект задания; другой payload с тем же ключом дает конфликт. Это защита приема внутри приложения, не обещание exactly-once внешнего платного API.
- Изменяемые операции содержат expected revision. Общая область Check.revision и таблица побочных изменений должны быть утверждены до ТЗ (ниже). Сервер проверяет актуальность вместе с записью, а не отдельным предварительным GET. В версии отзыва различаются отсутствие отзыва и revision 0.
- Прямой finalize из editing запрещен: требуется begin-completion и phase=review. Финализация одной транзакцией проверяет актуальную revision, отсутствие блокеров и допустимые отзывы, фиксирует snapshot и один AnalyticsJob. Двойной клик и второй браузер не создают второй запрос сводки.
- При редактировании до финала сервер заново вычисляет completion. Устаревшее `can_finalize=true` на клиенте не является разрешением финализировать новую версию.
- Поздний ответ старой попытки не возвращает удаленные сущности/отзывы и не подменяет новую версию. При удалении целой проверки отменяется будущая работа ее заданий, а поздний ответ не восстанавливает проверку.
- Чужой ID не дает доступа к объекту или фото. Для чужого объекта предлагается одинаковый `404`; неавторизованный запрос дает `401`, недостаточная роль staff — `403`. Конфликт версии/состояния — `409`, ошибочный файл/вход — `422`.
- После финала возможность менять отзывы по прежнему R46 отдельно не отменена. Изменение состояния отзыва не меняет зафиксированный состав, но делает прежнюю аналитику устаревшей. Изменение только комментария не меняет математические числа; его влияние на актуальность зависит от еще не утвержденного входа snapshot. Точный повторный запуск и UI этой ситуации нужно завершить в Q49 до выдачи окончательного ТЗ; молча показывать старый итог нельзя.

## Материалы для фиксации версии до начала работ

Из этого кандидата еще нужно получить единый комплект: `openapi.yaml` для HTTP, JSON Schema для доменных DTO и аналитики, типы клиента и валидные fixtures. Наличие этой страницы не означает, что эти файлы уже созданы или что Q49 закрыт. Сохраненные [ответы checker](../ai/README.md) переиспользуются без изменения, обертки приложения создаются отдельно.

Обязательные сценарии fixtures/контрактных проверок: одна страница с несколькими задачами; продолжение на двух фото; pending Job; отказ по фото; окончательный технический сбой; повторный submit; поздний ответ старой версии; согласие/красный отзыв/комментарий; конфликт отзыва; ожидание перед финалом; финальный submit аналитики; устаревшая сводка; чужой аккаунт.

Имена маршрутов и поля согласовываются до передачи индивидуальных ТЗ. После фиксации версии их нельзя независимо переименовывать. Совместимые добавления не ломают старые fixtures; несовместимое изменение требует явного обновления контракта и всех потребителей. Вечерняя сборка не должна впервые определять эти правила.

## Разрешение смешанного результата

Report.status=ok может содержать оцениваемую задачу и not_assessed. Нельзя пропускать весь Bundle ради одной неоценимой задачи. Для такого TaskAnalysis отдельно хранится разрешение `unresolved/skipped` и причина; это не Review и не удаление. Пропуск сохраняет отсутствие математического результата, не превращает тетрадь в полностью математически подтвержденную и не исключает хорошую соседнюю задачу из допустимого топа. Completion учитывает разрешение неоценимой задачи отдельно от оценки ИИ. Fixture mixed Report обязателен. Точная форма полей входит в доменную схему до выдачи ТЗ; checker не меняется.

## Блокирующие инженерные вопросы до заморозки ТЗ

1. **Идентичность и повторное выделение.** Описать атомарное замещение актуального набора результатов Bundle после новой InputVersion, различие повторной попытки той же версии и новой версии, судьбу уже удаленной Task/tombstone. Запрещены перенос согласий по похожей формуле и автоматическое восстановление удаленного. Нужен тест «было две задачи, после замены выделены три», в том числе после удаления одной. До определения политики автоматическая публикация такого неоднозначного замещения не считается поддержанной.
2. **Версии входа.** Фото загружаются/удаляются только у явно указанного текущего draft. Sealed InputVersion неизменяем; замена создает новую версию, старые результаты остаются историей. Полная схема должна разнести PhotoAsset и связь фото с версией и точно определить current_input_version_id при создании новой draft.
3. **Revision и сериализация.** Таблица «операция → проверяемая revision → увеличиваемая revision» должна охватывать создание/изменение фото, submit, публикацию worker, отзыв, skip, удаление и finalize. Все влияющие на finalize изменения используют общий транзакционный guard родительской проверки. Проверить гонки finalize с upload/review/worker publish, два клиента и stale can_finalize.
4. **Полный lifecycle аналитики Q49.** JSON-схемы/промпт, статусы, snapshot/data revision, влияние только комментария, явная операция повтора после failed и обновления после смены отзыва, допустимость спорных/пропущенных элементов, поздний старый ответ и непустой draft. GET summary не запускает новый запрос. Операции refresh/retry и их идемпотентность пока нужно добавить в замороженную версию; они не реализованы этой страницей.
5. **События и финансы.** Общая схема клиентских/серверных событий с дедупликацией, правила резервирования денег и конкурентности для двух типов Job, состояние неизвестного исхода и ручная пауза должны иметь отдельные сценарии и владельца обработки. Список enum сам по себе их не реализует.

До закрытия этих пунктов, появления OpenAPI/schema/валидных fixtures и финального независимого ревью три пакета нельзя объявлять готовыми к полностью независимому выполнению. Они не требуют новых математических полей в frozen checker или выбора технологии владельцем продукта.
