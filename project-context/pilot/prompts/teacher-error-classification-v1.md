# Дополнение к промпту: тип ошибки и математическое правило

Версия 0.1, 18.11.2026. Подготовлено по R37 в [DECISIONS.md](../DECISIONS.md). Готовый текст для подключения к запросу пилота; пока хранится как спецификация, не подключен к `SmartNoteLanding/app/prompts.py` и не проверен модельным прогоном.

## Текст для добавления к системной инструкции

```text
Классификация первой ошибки для учительской проверки:

1. Для первого ошибочного шага назови наблюдаемый тип ошибки и связанное математическое правило. Кратко объясни, как этот переход нарушает правило. Дай правильную запись только этого шага. Не добавляй ошибки последующих строк.

2. Используй единый каталог типов и правил, переданный со схемой. Одинаковое нарушение называй одинаково независимо от коэффициентов, ученика и номера задачи. Не создавай отдельную категорию для каждого примера. Идентификатор правила выбирай из каталога, только если такое поле предусмотрено схемой.

3. Описывай факт: «Не изменен знак при переносе слагаемого», «Не учтено ограничение: знаменатель не равен нулю», «Неверно вычислено частное». Для ОДЗ назови конкретное нарушенное ограничение. Не объявляй математической ошибкой одно отсутствие отдельной надписи «ОДЗ», если ограничения фактически соблюдены.

4. Не делай уверенных выводов о невнимательности или незнании ученика. Описка/опечатка – только возможная причина в пояснении, не основной тип ошибки и не отдельная категория топа. Основной тип связывай с математическим правилом. Если причина не установлена, не угадывай ее.

5. Не путай нечитаемую запись и ошибку ученика. Если существенный знак или строку нельзя прочитать надежно, используй подходящий отказ; не придумывай «опечатку».

6. Корректный незавершенный ход отмечай отдельно от математической корректности, без выдуманной ошибки. Само отсутствие завершения не добавляет ошибку для сводки. Не ищи незагруженные номера домашнего задания.

7. Возвращай только поля переданной JSON-схемы, по-русски в человекочитаемых строках. Не добавляй новые ключи только по этому тексту. Если отдельных полей правила нет, его смысл должен быть понятен в разрешенных label/explanation. Структурные поля добавляются только вместе с обновлением схемы приложения.
```

## Проектный каталог нормализации

Названия внутренних ID – техническое предложение. Каталог нужен, чтобы топ не распадался на синонимы ответа модели.

| ID | Название типа | Связанное правило |
|---|---|---|
| `equation_transposition_sign` | Знак при переносе слагаемого | Перенос меняет знак; эквивалентно выполняется одна операция с обеими частями |
| `equation_equivalent_operation` | Неравносильное преобразование уравнения | Одинаковая допустимая операция с обеими частями, ненулевой делитель |
| `distributive_property` | Раскрытие скобок | Множитель относится ко всем слагаемым |
| `minus_before_brackets` | Знаки после минуса перед скобками | Меняется знак каждого слагаемого |
| `like_terms` | Приведение подобных слагаемых | Складываются коэффициенты одинаковой буквенной части |
| `square_sum_identity` | Квадрат суммы или разности | Учитываются удвоенное произведение и знак среднего члена |
| `difference_squares_identity` | Разность квадратов | `a^2-b^2=(a-b)(a+b)` |
| `negative_inequality_operation` | Знак неравенства | При умножении/делении на отрицательное число знак меняется |
| `denominator_domain` | ОДЗ: знаменатель | Знаменатель не равен нулю |
| `even_root_domain` | ОДЗ: четный корень | В действительных числах подкоренное выражение неотрицательно |
| `principal_square_root` | Арифметический квадратный корень | Значение неотрицательно |
| `quadratic_formula` | Формула корней или дискриминанта | Применяется соответствующая формула с верными знаками и знаменателем |
| `arithmetic_operation` | Арифметическая ошибка | Корректно выполняется числовое действие |
| `other_observed_error` | Другая установленная ошибка | Назвать фактически нарушенный принцип, не придумывая причину |

По R39 возможная описка – только необязательная гипотеза в разборе, без отдельной категории топа и утверждения невнимательности как факта. Техническая схема/поле гипотезы может уточняться; одна первая ошибка не дает второе событие для среднего/топа.

## Связь с текущим контрактом и будущая проверка

В текущем `SmartNoteLanding/app/schemas.py` разрешены `error.code`, `label`, `explanation`, `corrected_latex`, а дополнительные поля запрещены. Семь значений старого `code` крупнее каталога правил. При реализации пилота выбрать версионированный способ передачи типа/правила и согласовать Pydantic, TypeScript, промпт и сводку. Добавление `rule_id` только в промпт без изменения схемы вызовет отказ валидации.

Проверить на [дев-примерах](../dev-examples/README.md): DEV02, DEV03 и DEV14 должны различать перенос, распределительное свойство и минус перед скобками. DEV04/DEV12 – арифметическое обоснование без утверждения доказанной невнимательности. DEV15/DEV16 – незавершенность без выдуманного неверного шага. Для ОДЗ использовать уже подготовленные DEV17/DEV18: ошибочное отсутствие ограничения знаменателя и корректно учтенное ограничение; не штрафовать только отсутствие подписи «ОДЗ».

Каталог, текст и возможные новые поля пока не являются проверенным поведением программы. При подключении зафиксировать версию промпта и результаты прогона.
